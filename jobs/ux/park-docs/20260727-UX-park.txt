WHAT'S IN THE SPEC (full detail in the tech doc, summarized in
jobs/ux/context/current.txt — not restated a third time here):

- BUG-53: two-line place chip (city bold + region/state) + a new, separate country row
  (my pill-vs-row call — row, reasoned against the card's existing one-row-one-meaning
  convention and multi-country trips). Flagged a real discrepancy between the tracker's
  "current state" description and what TripCard.tsx actually renders (it matches the
  trip-DETAIL place section instead) rather than silently guessing which surface was
  meant. Requires a small Backend field addition (country_name + new region_name on
  TripSummaryPlace.city) — both already computed by the underlying query, just not
  surfaced in the list-endpoint response mapper. Caught, by reading the repository code
  rather than assuming, that the existing trip.countries field is NOT a usable source for
  the new country row (it's fed by a different, mostly-empty-in-practice feature —
  trip_countries explicit associations, ADL-23 — not derived from places).
- UX-11: trip status (4 values/trip) and map shading state (7 values/place-aggregate) are
  different taxonomies — mapped the 2 with exact semantic matches (planning→planned,
  active→active) and deliberately gave Review and Locked the SAME shading colour
  (visited_once) rather than inventing a distinct-but-wrong mapping for Locked, with
  reasoning given. New real cost: a contrast-safe text-colour utility (S effort) for
  arbitrary admin-picked shading hex — everything else rides an already-shipped pattern
  (MapLegend.tsx already applies live shading colours as inline style).
- BUG-54: ruled NOT free — UX-11 gives a rendering technique, not the schema + admin UI
  BUG-54 actually needs. Stays parked, per the PO's own framing.
- BUG-47: suggestion-based design modeled on the app's existing IT-07 carry-forward
  accept/reject pattern, not a silent-write defaulting engine — avoids re-triggering the
  "never overwrite a user edit" problem this codebase already solved once (IT-11/DP-06).
  Deliberately thin, honest derivation table (restaurant→"Dining" only) rather than
  guessing at Experience items, which item_type (6 values) can't disambiguate against a
  17-entry free-text activity list.
- BUG-46: ruled FIX, not delete — BUG-47's suggestions are item-driven and no items exist
  yet at trip-create time, so the plain manual field stays load-bearing on create even
  after BUG-47 ships. Root cause confirmed in TripForm.tsx (single `isEditing &&` gate).
  Independent of BUG-47, can ship first.
