COMPLETED THREAD — S4: trip-list display, status pill colours, activities (2026-07-27)
================================================================================

  Brief: GitHub #274 (Wave 0 scoping brief S4, jobs/COO/backlog-clearance-plan.md §3).
  One spec pass, four tracker items batched because they share a surface (trip-list card)
  and a data system (Waypoint badges / per-user shading config). Deliverable:
  jobs/ux/tech/20260727-UX-triplist-status-activities-spec.md.

  BUG-53 (trip-list place display): flagged a discrepancy — the tracker's "current state"
  description ("city bold, country underneath") doesn't match what TripCard.tsx actually
  renders today (single-line, non-bold, no country at all); it matches the trip-DETAIL
  place-section header instead. Scoped to the list card anyway per the issue title, with
  the discrepancy stated explicitly rather than silently resolved. Design: two-line place
  chip (city bold + region/state, falls back to city-only when no region resolved — never
  duplicates country into that slot) + a NEW, separate country row (my pill-vs-row call:
  row, not merged into the category row — reasoning is the card's existing "one row = one
  meaning" convention, and that a merged row can't cleanly show multiple countries on a
  multi-country trip). Country row is deduped/ordered from trip.places client-side, NOT
  from trip.countries (checked: that field is fed by the separate trip_countries explicit-
  association table, ADL-23, and would render empty for most normal trips — a real trap
  caught by reading the repository code, not assumed). Requires a small Backend field
  addition (country_name + new region_name on TripSummaryPlace.city) — both joins already
  exist in tripRepository.getPlaces(), just not surfaced in the response mapper. No schema
  change.

  UX-11 (status pill colours vs shading): the real problem is that trip status (4 values,
  per-trip) and map shading state (7 values, per-place-aggregate) are different taxonomies
  — this can't be a lossless 1:1 mapping, and I said so explicitly rather than faking
  precision. Mapping: planning→planned, active→active (exact semantic matches), review_
  pending→visited_once, locked→visited_once (deliberately the SAME colour — rejected a
  locked→visited_multiple mapping because it could show "visited multiple times" on a
  trip's pill while the map correctly shows "visited once" for the same trip, a direct
  cross-surface contradiction; distinctness between Review/Locked carried by label text +
  the existing LockedIcon, not hue). Real new cost flagged: a contrast-safe text-colour
  utility (S effort) since admin-picked shading hex colours have no paired text colour and
  could be any lightness. Applies to StatusBadge for trip statuses in BOTH the list card
  and detail header (shared component) — explicitly not to item-status badges (no shading
  analogue at item level). Confirmed this rides an ALREADY-SHIPPED pattern (MapLegend.tsx
  already applies useShadingConfig() colours as inline style) — not new architecture, just
  the one contrast utility.

  BUG-54 (category/activity colour): ruled NOT free as a UX-11 side effect. UX-11 builds a
  reusable rendering technique; BUG-54 still needs a schema change (no colour column on
  categories/activities) and a net-new admin UI section, neither provided. Stays parked.

  BUG-47 (auto-populate activities): the honest constraint is that item_type is a 6-value
  enum and activities are a 17-entry free-text list (Skiing, Wine Tasting, Museum, etc.) —
  6 types cannot disambiguate 17 activities, so a full auto-derivation would mean guessing,
  and a wrong guess (e.g. any Experience item → "Sightseeing") is worse than no guess.
  Design: suggestion-based, modeled directly on the app's existing IT-07 carry-forward
  accept/reject pattern (already shipped, already tested) rather than a silent-write
  defaulting engine — this also sidesteps the "never overwrite a user edit" problem this
  codebase already solved once for IT-11/DP-06. Concrete derivation table: restaurant→
  "Dining" (the one reliable mapping), everything else → no suggestion, stated as a
  deliberate scope limit, not a gap. Self-contained frontend logic, no backend change.

  BUG-46 (activities missing from create): ruled FIX, not delete. BUG-47's suggestions are
  item-driven and no items exist yet at trip-create time (items are logged after trip+
  places are saved), so the plain manual field is still load-bearing on create even after
  BUG-47 ships — deleting it would regress, not simplify. Root cause confirmed in
  TripForm.tsx: single `isEditing &&` gate (line 324), same fix shape as Categories/
  Companions already use. Independent of BUG-47, can ship first.

  Tracker updated in place (BUG-53, UX-11, BUG-54, BUG-47, BUG-46) — status + GitHub #274
  + spec section reference in notes, per this session's brief scope. Did NOT touch owner
  fields, BRD, or brdRefs — flagged 3 new BRD ID recommendations (DP-07, DP-08, TR-16) for
  COO to add, per CLAUDE.md's BRD-gate rule (not mine to add).

  BUGS DISCOVERED: none new (this was audit-by-reading-source, not implementation) — but
  worth flagging forward: BUG-53's investigation surfaced that TripSummaryPlace.city's
  country_name is silently dropped by the list-endpoint response mapper despite already
  being computed by the underlying query — not a bug against any current requirement (list
  responses were never spec'd to include it), but exactly the gap this brief's Backend
  data-contract addition closes.

  GIT: Branch chore/ux-trip-list-spec. Spec-only + tracker + housekeeping commits. See
