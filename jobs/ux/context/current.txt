  Sourcing discrepancy caught and resolved (§0 of the spec): the brief pointed at

  was real; traced it to ADL-46-non-owner-access-model.md §4.3.1/§4.4.3 instead and worked
  from there. Flagged to COO rather than silently substituted.

  Design, top to bottom: a three-tier precedence rule (explicit user choice > trip-country-
  constrained suggestions > unconstrained discovery) governs every auto-suggestion in the
  flow. Country field is never silently auto-committed (the actual fix for Rome-Italy-vs-
  Rome-Georgia — a frontend sequencing change, no backend dependency). Region disambiguation
  refines, not replaces, the D14 mechanism already shipped un-spec'd on the in-flight
  release/adl46-access-model branch (PR #341) — labelling and optgroup grouping only.
  Pin-vs-no-pin: no fabricated placeholder pin (rejected as worse than none — wrong 100% of
  the time vs. sometimes), but a single combined "N places not yet located" map affordance
  (next to MapLegend, expandable, status-coded rows) rather than silent omission or two
  competing counters. Canonicalisation: rejected a canonical-name-plus-aliases data model
  outright (real complexity for a cosmetic want, and works against the convergence
  resolve-then-create exists for) — one-time disclosure instead, plus a cheap non-UX
  mitigation flagged to Backend (accept-language=en on the geocoder call). Disagreement
  case: deliberately given the SAME messaging as "not yet attempted" (pending) — the user's
  available action is identical either way, so a distinct alarm state would be new UI for
  no new decision.

  GE-16's correction mechanism ("re-point a place's city at any time") has zero UI today —
  confirmed by reading PlaceSection.tsx's header in full. Designed a standing, always-
  visible "Change city" control (not gated behind a status badge, since GE-16's right isn't
  conditional on status) that reuses the Add-Place search/create UI as a shared component,
  PATCHing city_id instead of creating a new place. Backend dependency named precisely: the
  PATCH accepting city_id (ADL-46 D11) exists on release/adl46-access-model but NOT yet on
  main — verified both by reading places.ts on each ref, not assumed.

  /cities/:id (CityItemsPage, IT-09) assessed in full per the brief's instruction to fold it
  into this spec rather than treat it separately: solid craft (proper Waypoint tokens,
  reuses shared components) but a real defect independent of this spec — its header has no
  data source of its own (relies on router location.state, degrades to "This city" on a
  refresh or direct link) — plus the additions this spec now needs from it (location-status
  display, a "visited on N trips" line, explicitly NOT a city-editing form, since the fix
  action is place-scoped per D11, not city-scoped).

  One correction made mid-investigation and left visible rather than silently fixed: I
  initially misjudged trip_countries as a schema-only, UI-less field (a naming-mismatch
  grep miss — grepped the Drizzle symbol, not the frontend's own field name) before a
  second probe (reading TripForm.tsx) found a fully-built optional Countries multi-select
  already submitting it. Corrected before it reached the spec as a claim — the two-probe
  rule catching its own near-miss, worth recording since it changed a real design
  recommendation's framing (tier 2 is immediately usable, not a follow-on dependency).

  Data-model implications named for the Architect (spec §7): region_name needed on
  city-facing responses (parallel to the D-04 country_name precedent); a stable city-
  metadata source for CityItemsPage's header; explicitly NO new city state and NO alias
  table (both evaluated and rejected in the spec itself, not left as open questions); one
  new Waypoint badge hue (`unlocated`, orange/hue 45) for the "location not found" state,
  named as a small new token, not assumed free.

  One thing I could not verify (stated as UNVERIFIED in the spec, not silently assumed):

  ADDENDUM (same day, two follow-up COO messages) — §11 and §12 added to the same file/PR:

  §11 answers "how does a user actually resolve an unlocated place," as one recommended
  design (not a menu), per explicit PO instruction to show it as worked flows with named
  examples rather than abstract state names. Read the actual current backend disposition
  space first (jobs/architect/tech/20260801-ADL46-F1-F2-ruling.md, which now exists — the
  file my original brief pointed at under a different name was created for real the same
  day, after my first pass; see below) rather than working from my own original taxonomy.
  Core call: three user-facing remedy buckets (wait / pick / re-point-or-dismiss), NOT the
  backend's four internal dispositions — collapsed `region-unconfirmed` into "wait" because
  it has no second candidate to offer despite being technically "ambiguous," on the same
  principle already used elsewhere in the spec (a distinction that doesn't change the
  available action doesn't earn separate UI). Added a promotion rule the backend ruling
  makes necessary but doesn't itself provide: a `pending` row that has exhausted its retry
  budget must read as terminal in the UI even though the backend never marks it
  `unresolvable` — continuing to say "still confirming" past that point would be dishonest.
  Four worked flows written to the brief's exact four cases (ambiguous Springfield, offline-
  created Lyon, an unresolvable fictional hamlet, wrong-Rome-Georgia) using named personas.
  On the dropped-pin idea the COO/PO already rejected: agreed with the rejection on my own
  reasoning (same catalogue-drift shape as my own alias-name rejection), not deference —
  and named the one place the COO's stated reasoning is weaker than claimed (the effort-

  §12 scopes an MVP after a second COO message reframed the whole feature as probably-edge-

  carries an explicit ADL-46 D11 comment, and the route handler) — but PlaceDateForm.tsx is

COMPLETED THREAD — S4: trip-list display, status pill colours, activities (2026-07-27)
================================================================================

  Brief: GitHub #274 (Wave 0 scoping brief S4, jobs/COO/backlog-clearance-plan.md §3).
  One spec pass, four tracker items batched because they share a surface (trip-list card)
  and a data system (Waypoint badges / per-user shading config). Deliverable:
  jobs/ux/tech/20260727-UX-triplist-status-activities-spec.md.

  BUG-53 (trip-list place display): flagged a discrepancy — the tracker's "current state"
  description ("city bold, country underneath") doesn't match what TripCard.tsx actually
  renders today (single-line, non-bold, no country at all); it matches the trip-DETAIL
  place-section header instead. Scoped to the list card anyway per the issue title, with
  the discrepancy stated explicitly rather than silently resolved. Design: two-line place
  chip (city bold + region/state, falls back to city-only when no region resolved — never
  duplicates country into that slot) + a NEW, separate country row (my pill-vs-row call:
  row, not merged into the category row — reasoning is the card's existing "one row = one
  meaning" convention, and that a merged row can't cleanly show multiple countries on a
  multi-country trip). Country row is deduped/ordered from trip.places client-side, NOT
  from trip.countries (checked: that field is fed by the separate trip_countries explicit-
  association table, ADL-23, and would render empty for most normal trips — a real trap
  caught by reading the repository code, not assumed). Requires a small Backend field
  addition (country_name + new region_name on TripSummaryPlace.city) — both joins already
  exist in tripRepository.getPlaces(), just not surfaced in the response mapper. No schema
  change.

  UX-11 (status pill colours vs shading): the real problem is that trip status (4 values,
  per-trip) and map shading state (7 values, per-place-aggregate) are different taxonomies
  — this can't be a lossless 1:1 mapping, and I said so explicitly rather than faking
  precision. Mapping: planning→planned, active→active (exact semantic matches), review_
  pending→visited_once, locked→visited_once (deliberately the SAME colour — rejected a
  locked→visited_multiple mapping because it could show "visited multiple times" on a
  trip's pill while the map correctly shows "visited once" for the same trip, a direct
  cross-surface contradiction; distinctness between Review/Locked carried by label text +
  the existing LockedIcon, not hue). Real new cost flagged: a contrast-safe text-colour
  utility (S effort) since admin-picked shading hex colours have no paired text colour and
  could be any lightness. Applies to StatusBadge for trip statuses in BOTH the list card
  and detail header (shared component) — explicitly not to item-status badges (no shading
  analogue at item level). Confirmed this rides an ALREADY-SHIPPED pattern (MapLegend.tsx
  already applies useShadingConfig() colours as inline style) — not new architecture, just
  the one contrast utility.

  BUG-54 (category/activity colour): ruled NOT free as a UX-11 side effect. UX-11 builds a
  reusable rendering technique; BUG-54 still needs a schema change (no colour column on
  categories/activities) and a net-new admin UI section, neither provided. Stays parked.

  BUG-47 (auto-populate activities): the honest constraint is that item_type is a 6-value
  enum and activities are a 17-entry free-text list (Skiing, Wine Tasting, Museum, etc.) —
  6 types cannot disambiguate 17 activities, so a full auto-derivation would mean guessing,
  and a wrong guess (e.g. any Experience item → "Sightseeing") is worse than no guess.
  Design: suggestion-based, modeled directly on the app's existing IT-07 carry-forward
  accept/reject pattern (already shipped, already tested) rather than a silent-write
  defaulting engine — this also sidesteps the "never overwrite a user edit" problem this
  codebase already solved once for IT-11/DP-06. Concrete derivation table: restaurant→
  "Dining" (the one reliable mapping), everything else → no suggestion, stated as a
  deliberate scope limit, not a gap. Self-contained frontend logic, no backend change.

  BUG-46 (activities missing from create): ruled FIX, not delete. BUG-47's suggestions are
  item-driven and no items exist yet at trip-create time (items are logged after trip+
  places are saved), so the plain manual field is still load-bearing on create even after
  BUG-47 ships — deleting it would regress, not simplify. Root cause confirmed in
  TripForm.tsx: single `isEditing &&` gate (line 324), same fix shape as Categories/
  Companions already use. Independent of BUG-47, can ship first.

  Tracker updated in place (BUG-53, UX-11, BUG-54, BUG-47, BUG-46) — status + GitHub #274
  + spec section reference in notes, per this session's brief scope. Did NOT touch owner
  fields, BRD, or brdRefs — flagged 3 new BRD ID recommendations (DP-07, DP-08, TR-16) for
  COO to add, per CLAUDE.md's BRD-gate rule (not mine to add).

  BUGS DISCOVERED: none new (this was audit-by-reading-source, not implementation) — but
  worth flagging forward: BUG-53's investigation surfaced that TripSummaryPlace.city's
  country_name is silently dropped by the list-endpoint response mapper despite already
  being computed by the underlying query — not a bug against any current requirement (list
  responses were never spec'd to include it), but exactly the gap this brief's Backend
  data-contract addition closes.
