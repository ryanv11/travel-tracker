2. ADL-28 RISKS — how each was addressed
===============================================================================

R1 (shading query isolation was silently absent): getAllCountryShading,
getCountryShading, and getRegionShading were ALREADY userId-scoped before this brief —
that was HC-03 (2026-07-15, commit cf7ea36), discovered by reading the actual service
file rather than assuming the ADL's risk description was still 100% current as of
today. What THIS brief fixed under the R1 umbrella: getCityShading (previously
unscoped, joining ALL users' trips with no filter — a real, confirmed isolation gap)
and the config layer (see R2). Verified via services/__tests__/shading.user-scope.test.ts
(pre-existing, still green) plus the new coverage in routes/__tests__/map.test.ts.

R2 (cache invalidation scope): the config cache was a single global
`Map<stateKey, {colorHex, displayName}>`. Changed to `Map<userId, ShadingConfigMap>`.
invalidateConfigCache(userId) now clears only that user's entry;
invalidateConfigCache() with no arg clears everything (kept for test resets — several
existing tests called it bare and I didn't want to force unrelated test files to learn
a new required param). Verified with a dedicated test in routes/__tests__/map.test.ts:
PATCH by user A does not affect user B's already-cached config.

R3 (migration data loss on no-owner state): not this brief's concern — that was steps
1-4 (Database brief, PR #240), already closed.

R4 (trip_companions_map cross-user enforcement is application-only): implemented in
tripRepository.replaceAssociations — calls companionRepository.validateOwnership(userId,
companionIds) before the batch insert, throws ValidationError (400, not 404 per the
ADL's explicit instruction) if any ID is invalid. Explicitly tested in
repositories/__tests__/trips.test.ts (3 new cases: valid own companion accepted, another
user's companion rejected 400, nonexistent companion ID rejected 400) — this was the
single most safety-critical piece of this brief per the ADL's own framing ("this must
be tested explicitly").

3. DEVIATION FROM BRIEF — e2e admin.spec.ts companion test
===============================================================================

The brief said both of the schema-migration brief's `.skip`'d tests should be
"un-skipped and rewritten... do not leave them skipped." I did this fully for the
backend contract test (owner-access.test.ts) — deleted it, replaced with non-skipped
coverage in the new routes/__tests__/companions.test.ts.

For src/e2e/admin.spec.ts's Playwright test ("create companion appears in list"), I
could NOT genuinely un-skip it within this brief's scope. That test drives the real
browser UI (the Admin panel's CompanionTab), which calls
src/frontend/hooks/useAdmin.ts — and that hook still POSTs to /api/admin/companions,
the exact route this brief removed. No backend-only change can make that e2e test pass;
fixing it requires editing frontend code, which is out of a Backend brief's role scope
(and I don't know what else might be in flight on the frontend right now, so making an
opportunistic one-line fix there felt like the wrong call without a brief for it).

What I did instead: left the test `.skip`'d but rewrote its comment to accurately
describe the CURRENT blocker (frontend, not backend) rather than leaving the old
comment that pointed at a Backend brief that has now shipped — an inaccurate skip
comment is worse than an honest one. Flagging this explicitly here and in the
completion report: a small Frontend follow-up brief is needed (repoint
useAdmin.ts's companion calls at /api/companions), after which this e2e test should
pass unmodified.

I considered deleting the skipped test outright instead of just updating its comment,
on the theory that a stale-but-updated skip is still clutter. Kept it because it's the
clearest signal to whoever picks up the Frontend follow-up brief that there's a
specific e2e test waiting to be un-skipped — deleting it would lose that thread.
