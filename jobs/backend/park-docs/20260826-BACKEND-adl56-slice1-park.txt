THE TWO N5 TRAPS — WHY THE OBVIOUS IMPLEMENTATION GETS BOTH WRONG
================================================================
§6b(1) PLACEMENT. The backfill must never reach the caught-violation
mergeIntoWinner branch: that branch repoints trip_places onto a PRE-EXISTING
winner (someone else's row, which may hold a user-SUPPLIED region) and deletes
the loser. Backfilling there overwrites a user value while nominally "filling a
blank" — a D12 rule-3 breach on the path where it is least visible.

  The structural reason it holds: the backfill rides the SAME single UPDATE
  statement as the OSM stamp. A uniq_cities_osm_ref violation rolls the whole
  statement back atomically, so the catch branch inherits nothing. This is not
  defensive ordering, it is why §6b(1) says "the try-block direct update" rather
  than "remember not to". The [S1][GUARD] test exercises the REAL partial unique
  index against real libSQL (the loser row is genuinely deleted), so the branch
  is proven taken, not simulated.

§6b(2) DERIVATION. classifyCandidates returns `best = eligible[0]`, and
eligible[0] CAN carry a NULL region_iso while the resolve is region-unambiguous:
  eligible = [ {regionIso: null}, {regionIso: 'AU-VIC'} ]
  → distinctRegionIsos = ['AU-VIC'] (length 1 → verdict 'ok')
  → best.regionIso === null
Reading `best.regionIso` passes the headline test and silently reproduces BUG-98
for exactly the rows D4 exists to fix, with nothing red anywhere. Derive from the
SET. Both N5(b) tests (create path and resolver) exist solely to tell those two
implementations apart, and both are green.

COO ADDITION 2 — VERDICT: §3b(7)'s ROLLBACK SEAM IS ENTIRELY FRONTEND
================================================================
Backend holds NO part of the live-lookup trigger policy. Two probes that fail
differently:
  (a) grep of all backend source (excluding __tests__) for
      autofire|auto_fire|LIVE_AUTOFIRE|debounce|'auto'..'manual'|settledQuery
      → zero hits.
  (b) read src/backend/routes/geocode.ts in full — a stateless per-request proxy:
      validateQuery → pick DISCOVERY_LIMIT/CONSTRAINED_LIMIT → nominatimSearch →
      serialize. No trigger, no debounce, no session cache, no policy switch, no
      state between requests. Its own header describes the cadence as the
      CALLER's ("one upstream request per keystroke-settle").
  Corroborating: every caller of lookupCityCountry is in src/frontend
  (AddPlaceFlow.tsx:410, useCityDisambiguation.ts:59).
The backend owns the RATE chokepoint (nominatim-client's serialized 1 req/s
egress) — a different control from the TRIGGER §3b(7) is about, and one that is
already isolated. So there is no backend `enabled: 'auto' | 'manual'` seam to
build, and inventing a backend flag nothing reads would be the token constant the
COO explicitly did not want. COO to carry §3b(7) into the frontend brief.
