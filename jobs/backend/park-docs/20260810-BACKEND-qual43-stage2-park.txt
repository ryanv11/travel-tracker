re-expressed.

3. THE TWO AXES — WHY ONLY SOME PREDICATES COMPOSE THE CHOKEPOINT
================================================================

This file now holds ownership predicates AND creator predicates, and they are
not the same thing. Both module headers say so, because the next reader will
otherwise "fix" one of them.

  COMPOSES scopeToUser (user-owned):
    findCarryForwardItems  -> scopeToUser(trips, userId)
    findCityItems          -> scopeToUser(items, userId)
  Cities' user-owned JOINS join the chokepoint even though cities does not.

  HAND-WRITTEN, CORRECTLY (global reference data):
    search's GE-16 containment            cities.createdByUserId
    findRegionlessUpgradeCandidate's
      creator-or-null upgrade scoping     cities.createdByUserId
  These are CREATOR-VISIBILITY / write-through-scoping on a global table
  (nullable created_by_user_id, ON DELETE SET NULL), not row ownership. The
  type system enforces the distinction: `cities` is deliberately absent from
  UserOwnedTable, so passing it to scopeToUser is a compile error.
  scripts/scope-completeness-check.sh does not flag them either — its regex
  matches `.userId`, and the column is `.createdByUserId`. That is a correct
  pass, not a lucky one, but it is worth knowing it is regex-shaped: a future
  rename of the column to `.userId` on a global table would silently start
  matching. Flagged, not fixed — widening or narrowing that check is not an
  implementation brief's call (OP-30).

SQL EQUIVALENCE was protected the same way Stage 0 protected it: the term
ORDER inside each and(...) is unchanged, so the emitted SQL is byte-identical
rather than merely logically equivalent. Both sites had the predicate in the
middle of the condition list, so neither could use ownedAnd (which puts scope
first) without reordering. Using scopeToUser positionally was the cheaper
equivalence argument.

4. THE NEW TESTS — AND WHY THEY ARE NOT VACUOUS
================================================================

src/backend/services/__tests__/cityIdentityService.test.ts, 19 tests, using
repositories/__tests__/test-db.ts (real migrations replayed into :memory:,
PRAGMA foreign_keys = ON).

MOCK FIDELITY (QUAL-22, the brief's explicit requirement). Nothing stubs
insertCityOrReuse's catch path. The violations are produced by the database:
  uniq_cities_osm_ref             UNIQUE(osm_type, osm_id) WHERE osm_id NOT NULL
  uniq_cities_pending_per_creator UNIQUE(name NOCASE, country, COALESCE(region,0),
                                  COALESCE(creator,'')) WHERE status='pending'
Both are exercised by separate tests that provoke them for different reasons.
FKs being ON is what makes "a NON-unique constraint error is rethrown, not
swallowed into a false reuse branch" a real assertion — isUniqueViolation is
deliberately narrow, and that narrowness is now tested rather than trusted.

The race test does not fake the race at the boundary: the mocked
resolveByOsmId INSERTS the competing row as a side effect between the ref
check and this request's insert, so the live index is what rejects the second
insert and the re-select is what recovers.

  A. removed `if (!isUniqueViolation(err)) throw err;`
     -> "rethrows a constraint error that is NOT a unique violation" FAILED

     -> "declines a resolved region-less row" FAILED
Both files restored from a scratch-dir copy (never `git stash` — refs/stash is
shared across worktrees, OP-20) and re-verified green.

DELIBERATELY NOT ASSERTED: cross-tenant OWNERSHIP isolation on `cities`. There
is none to assert — cities are global reference data — and a test pretending
