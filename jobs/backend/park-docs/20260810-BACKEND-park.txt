THE TWO DIVERGENCES (flagged to COO — preserved, not collapsed)
================================================================
DIVERGENCE 1 — the two trips.ts place maps are NOT the same shape.
  The COO brief called them "the same place shape mapped two ways". My probe
  found they are deliberately different: the LIST (buildTripResponse) is a
  minimal "city pin" ({id,city_id,city}) — its own comment said so — and the
  DETAIL (GET/:id) is the full place (dates + activities + items, city with
  country_name). Both read the SAME tripRepository.getPlaces rows, so the data
  is available in both; the LIST simply omits it on purpose. Collapsing them to
  one identical output would ship every place's items+activities+country_name
  inside every trip of the trips-list response — a real payload/behaviour change.
  RESOLUTION: removed the DUPLICATION (both now share serializeCityWithRegion/
  serializeCityWithCountry + the place serializers) while preserving each
  endpoint's distinct shape. This is the honest reading of AC#3.

DIVERGENCE 2 — the city response shape has 3 variants across the API.
  base (cities POST/PATCH — those queries don't LEFT JOIN regions, so no
  region_iso/region_name), base+region (cities GET/:id, places GET/POST, trips
  LIST), base+region+country (trips DETAIL only — only getPlaces LEFT JOINs
  countries). These reflect which tables each query joins. Making them uniform
  (the "union is the right shape" instinct) would ADD fields to several
  responses — a behaviour change and, for a raw userId-style field, exactly the
  "newly EXPOSE a field" hazard the OP-06 note warns against. So each variant is
  preserved byte-identical and the uniformity question is a FOLLOW-UP, not this
  refactor. Candidate latent persisted-but-dropped bugs living in the gap:
  cities POST/PATCH omit region_iso/region_name; every city site except trips
  DETAIL omits country_name. Worth a COO/PO call on whether to close them (would
  need the queries to join regions/countries + a shape change).

src/backend/routes/__tests__/serializer-characterization.test.ts (16 tests).
Pins the EXACT sorted key set of every trip/place/city/item response + the
load-bearing values (region_name, region_iso, country_name, arrived_on,
departed_on). Compares parsed-object key SETS, not raw bytes — JSON key ORDER is
not part of the contract (the composed serializers append region/country fields,
so key order shifts; presence + value are identical). If a future edit drops a
field, one of these fails loudly.
