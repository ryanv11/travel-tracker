TASK
The Add Place city autocomplete renders one line per row as
`{city.name} {city.country_code}`, so an ambiguous city shows as
"Springfield US" with nothing distinguishing which Springfield the user is
selecting. PO decision: show city, state, country. This brief is the
backend half only — extend GET /api/cities so each row carries the
region's human-readable name and ISO code via a join on `regions`.
Frontend's AddPlaceFlow.tsx label change is a separate, deliberately-held
brief (OP-28 collision avoidance) — not touched here.

WHAT WAS CHANGED

1. src/backend/routes/cities.ts — GET /api/cities (search) handler:
   - Added `leftJoin(regions, eq(regions.id, cities.regionId))`.
   - Added `region_name: regions.name` and `region_iso: regions.iso3166_2`
     to the select object, alongside the existing `region_id: cities.regionId`
     (kept unchanged for existing consumers, per the brief).
   - LEFT JOIN, not INNER, is the entire point: an INNER join would silently
     drop every row with a NULL region_id (any city in a non-region-tier
     country, or a region-tier city not yet assigned a region) out of the
     result set entirely — a real regression indistinguishable from missing
     data, and one that would narrow the GE-16 containment predicate
     (cities.ts:60-64, `or(resolved, mine, creator IS NULL)`) it sits next
     to. The containment predicate itself is untouched — same three
     conditions, same `and(...conditions, containment)` composition, just
     one more join upstream of it.
   - Naming: followed the existing `region_iso` precedent already used by
     repositories/trips.ts (`cityRegionIso: regions.iso3166_2`) and
     routes/trips.ts / geocode.ts (`region_iso` in the response), rather
     than the `iso_3166_2` spelling used in admin.ts/map.ts's region-listing
     endpoints — this endpoint is city-shaped, not region-shaped, so it
     mirrors the sibling city-with-region join in trips.ts rather than the
     admin CRUD endpoints.

2. [SUPERSEDED — see PR REVIEW UPDATE at bottom of this doc; tests moved to
   src/backend/routes/__tests__/cities.search-region-enrichment.test.ts]
   Originally landed as a new describe block "BUG-72 — GET /api/cities
   region enrichment" (3 tests) appended directly in
   adl46-access-model.test.ts, after the existing "ADL-46 Group C — pending
   vs resolved city containment (GE-16)" block, since it shared that
   block's seed helpers (seedCountry, seedRegion, seedCity) and that file
   already owned GET /api/cities route-level coverage:
   - a region-tier city (US/Colorado) carries region_id + region_name +
     region_iso together.
   - a region-less city (JP/Kyoto, non-region-tier country, NULL
     region_id) still appears in results, with region_name/region_iso both
     null — this is the success-criteria-mandated proof that the LEFT JOIN
     does not narrow GE-16 containment. Chose a different country/geocode
     path (JP, not reusing the existing C1/C3 pending-city fixtures) so
     this test is a direct, single-purpose proof of the join behaviour
     rather than riding on containment-test fixtures that exercise a
     different axis (creator scoping).
   - a mixed search (US/Illinois) returns one regioned row and one
     region-less row from the same country in a single response, to catch
     any per-row query-construction mistake that a single-row test could
     miss.
   All three run as an authenticated owner (mockIsOwner=1) — no access-
   control dimension under test here, unlike Group C.

3. jobs/backend/tech/20260307-api-reference.md — GET /api/cities section:
