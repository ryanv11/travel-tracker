2. THE MECHANISM SPLIT AS APPLIED (ADL-53 §5.1 / §2)
----------------------------------------------------------------
PREDICATE-COMPOSED — the target table carries its own user_id, so
ownership is the chokepoint predicate:

  a) fetchItemsWithExtensions (items-helper.ts:87)
     `git mv src/backend/routes/items-helper.ts
             src/backend/repositories/items-helper.ts`
     Signature: fetchItemsWithExtensions(userId, conditions?, opts?)
     — userId is REQUIRED and first. The helper composes ownership
     itself: `.where(ownedAnd(items, userId, conditions))`. Callers
     no longer thread the scope through `conditions`; a caller that
     forgets it does not compile.

     ADL-53 calls this the single highest-value relocation in the
     stage and it is. It also fixed a layering inversion nobody had
     listed: repositories/items.ts was importing a query out of
     routes/.

     F3 footgun checked: this builder has exactly ONE terminal
     .where(). A comment at the call site records that any future
     branch must repeat ownedAnd in EVERY terminal .where(), because
     Drizzle's .where() overwrites rather than appends.
     No LEFT JOIN ON-clause predicate was moved to a WHERE anywhere
     in this stage — the five extension left-joins keep their ON
     clauses untouched, so no join silently became an INNER JOIN.

  b) trips.ts:198 items read -> itemRepository.findByTrip(userId, tripId)
     The handler hand-built a trip-plus-owner conjunction and called
     the helper directly. findByTrip composes exactly those two terms
     and passes the same (all-undefined) opts object, so the orderBy
     branch and the minRating branch both resolve identically. This
     is a call-site swap, verified term by term before switching.

  c) places.ts carry-forward SEC-02 check
     -> itemRepository.findOwnedIds(userId, ids), which composes
     ownedAnd(items, userId, inArray(items.id, ids)). Returns [] for
     an empty id list without a round trip (inArray([]) already
     returned no rows, so same result).

ASSERTION-GUARDED — the target has no user_id column, so it INHERITS
isolation and composes nothing. The prior ownership assertion IS the
isolation; none was dropped, none was replaced by a predicate:

  d) trips.ts trip_place_activities_map join
     -> placeRepository.findActivitiesForPlaces(placeIds).
     Merged with the byte-identical copy already inside
     placeRepository.findByTrip — one join, two consumers (PO standing
     reuse preference). The trips route's mapping changed from
     a.activityId/a.activityName to a.id/a.name; same output shape.
     tripRepository.findByIdOrThrow stays exactly where it was: its
     404 is what stops a non-owner reaching that line.

  e) places.ts activity tag/untag
     -> placeRepository.isActivityTagged / addActivityTag /
        removeActivityTag.
     The route's placeRepository.findById(userId, placeId) stayed.
     It is itself the ownership assertion — it composes
     scopeToUser(trips, ...) through an inner join — and the handler
     needs its result for the place's tripId regardless, so moving it
     into the repository would have bought a second query and nothing
     else. Route control flow is textually unchanged: ownership check,
     activity-ownership check, lock check, duplicate check, mutate.
     Audit invariant 17 (ownership BEFORE lock) preserved.

  f) places.ts carry-forward trip_places read
     -> placeRepository.findInWritableTrip(userId, tripId, placeId),
     which calls this.assertWritable INTERNALLY. The route's separate
     assertWritable call was removed because it moved, not because it
     was dropped. This mirrors placeRepository.delete/updateDates,
     which already assert internally before an identical `existing`
     select. Ordering preserved exactly: NotFoundError (404, opaque
     per SE-05) before LockError (403), so a non-owner still never
     learns a trip is locked.

4. THINGS THE NEXT AGENT SHOULD KNOW
----------------------------------------------------------------
- assertOwned STILL has no production caller. The brief expected Stage
  4 to be its first; it is not, and I did not manufacture one. Every
  assertion-guarded read in this stage already sits behind a STRONGER
  gate that itself composes scopeToUser (assertWritable for the write
  paths, a scoped findById/findByIdOrThrow for the read paths).
  Forcing assertOwned in would have meant a redundant SELECT per
  request to satisfy a checklist. It remains the right shape for a
  read-gate on a trip whose owner is not otherwise looked up — that
  site does not exist yet. Its correctness is not in doubt; only its
  caller count.

- itemRepository.update's read-back is now owner-scoped, a consequence
  of making userId required. Invisible through the routes (items.ts
  PATCH runs assertWritable + findRawByIdOrThrow first). It differs
  only on a direct repository call by a non-owner: previously returned
  the owner's untouched row, now returns null. The existing repository
  test for that path does not assert the return value and stays green;
  its COMMENT now describes the old behaviour, which I left alone
  because the brief forbids touching existing test files. Worth a
  one-line comment fix in some later pass.

- PRE-EXISTING GAP, NOT FIXED (would have been a behaviour change, and
  no relocation touches it): itemRepository.update calls
  updateExtension() regardless of whether the scoped UPDATE matched
  any row, and the extension tables (item_flights, item_hotels, ...)
  carry no user_id of their own — they are assertion-guarded by the
  caller. Unreachable via HTTP for the same reason as above. If
  someone adds a route that calls itemRepository.update without a
  prior ownership assertion, that becomes live. Flagged, not fixed.

- Stage 5's guard flip: Check 2 is at zero and Check 1 Zone B is at
  zero, so promoting BOTH to enforced should be a one-line change per
  zone with no follow-on work. Note the script matches TEXT, not
  syntax — once flipped, a comment quoting `getDb` or the predicate
  form will red the build. That is by design; reword the comment.
