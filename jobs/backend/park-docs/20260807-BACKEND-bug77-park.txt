WHAT WAS BUILT

1. src/backend/services/nominatim-client.ts
   - RawNominatimResult.address gains `state?: string` and `country?: string`
     (both already present in the raw Nominatim payload under the existing
     format=json&addressdetails=1 request shape — confirmed against the
     committed fixtures at __tests__/fixtures/nominatim/bug76/denver_us.json
     and springfield_us.json, e.g. address.state="Colorado",
     address.country="United States").
   - NominatimCandidate gains `stateName?: string | null` and
     `countryName?: string | null` — named distinctly from the existing
     `regionIso`/`countryCode` (which carry ISO codes, not names) so the two
     pairs can't be confused at a call site. `county` already existed
     (BUG-75 v3) and needed no change.
   - parseCandidate now sets `stateName: raw.address?.state ?? null` and
     `countryName: raw.address?.country ?? null`.

2. src/backend/routes/geocode.ts
   - candidates.map(...) gains three additive fields per candidate: `state`,
     `country` (the names), `county` (already computed, just not previously
     serialized onto the wire). Everything else in the mapping — name,
     display_name, country_code, region_iso, latitude, longitude, osm_type,
     osm_id — is byte-for-byte unchanged.

3. src/frontend/types/api.ts
   - GeocodeCandidate gains `state?: string | null`, `country?: string | null`,
     `county?: string | null`, optional for the same reason osm_type/osm_id
     are (existing hand-written fixtures predate the field). Type-only change
     — no frontend consumption logic added; that's the follow-up brief's job.

4. src/backend/routes/__tests__/bug77-geocode-names-e2e.test.ts (new)
   - Follows the bug76-geocode-e2e.test.ts pattern (QUAL-22 mock-fidelity):
     only global.fetch is stubbed with the exact committed fixture bodies
     (denver_us.json, springfield_us.json) — the real route, real
     nominatimSearch, real parseCandidate all run unmocked. A service-boundary
     mock could pass vacuously by handing the route pre-shaped candidates
     that were never actually produced from raw Nominatim JSON; this can't.
   - 4 assertions: Denver CO carries state="Colorado"/country="United
     States"/county=null (consolidated city-county, no county key in that
     candidate's own address block — proves real fixture data, not a
     hardcoded stand-in); Denver IA (same-state-name duplicate within the
     same response) carries county="Bremer County" for disambiguation;
     Springfield IL carries all three; pre-existing fields
     (name/display_name/country_code/region_iso) are asserted unchanged
     alongside the new ones.
