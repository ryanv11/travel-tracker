WHY THIS EXISTED
--------------------------------------------------------------------------
/health returned {status:'ok'} and nothing else. From a browser, "the fix is

WHAT SHIPPED
--------------------------------------------------------------------------
1. src/backend/services/build-info.ts (NEW)
   resolveBuildInfo() reads, in order:
     BUILD_COMMIT_SHA (operator override)
     RAILWAY_GIT_COMMIT_SHA (platform-injected)
     src/backend/generated/build-info.json (baked at build time)
     -> "unknown"
   Design points that are load-bearing rather than decoration:
   - Candidates are validated against /^[0-9a-f]{40}$/. A typo, a truncated
     value or a platform placeholder degrades to "unknown". A marker that
     LOOKS like a commit but is not is strictly worse than no marker, because
     it answers "is my fix deployed?" confidently and wrongly.
   - builtAt is only carried when the baked file's own commit equals the
     resolved SHA. Otherwise you would pair commit A with build time B.
   - Memoised: the build cannot change under a live process, and /health is a
     pollable liveness endpoint.
   - `source` is returned to callers but is logged at startup ONLY, never over
     HTTP. It is operator diagnostics ("the resolver fell back"), not
     something a public endpoint should volunteer.

2. /health — server.ts AND server-test-app.ts, same handler shape
   {status:'ok', commit, commitFull, builtAt}. `status` unchanged and first.
   Kept identical in the test app deliberately, so integration tests exercise
   the real payload rather than a stub that can drift.

3. scripts/generate-build-info.js + npm "prebuild"
   Resolves BUILD_COMMIT_SHA -> RAILWAY_GIT_COMMIT_SHA -> GITHUB_SHA ->
   `git rev-parse HEAD`, writes src/backend/generated/build-info.json.
   Gitignored: a committed copy is stale one commit later.
   Never fails a build — writes commit:null and warns.
   Fires on Railway because Railpack runs `npm run build` for this service
   (empirically: staging serves dist/ per ADL-32, which only exists if
   `vite build` ran there).

4. Frontend — deliberately tiny

   unidentifiable or /health fails: no spinner, no error surface.
   Mounted in App.tsx's EXISTING nav right-hand group. That group now owns

   vite.config.ts proxies /health to :3001 in BOTH server and preview blocks

5. Shakedown check 5 (src/e2e-shakedown/shakedown.spec.ts)
   Renamed to "/health answers and reports the build SHA within the
   deploy-propagation window".
   - ALWAYS records the deployed SHA: console.info + testInfo.annotations, so
     it lands in shakedown-results.json and the uploaded artifact.
   - When SHAKEDOWN_EXPECTED_SHA is set, the existing 10x6s retry window is
     spent waiting for the deployed SHA to MATCH, not merely for a 200. A
     rollout in flight still passes; a deploy that never happened fails, with
     an error naming Railway SKIPPED deploys explicitly.
   - Unset (local run, or a base_url override) => report, do not verify. Said
     plainly in the annotation text.
   Workflow: only a step-level `env:` was added. SHAKEDOWN_EXPECTED_SHA is
   `${{ inputs.base_url == '' && github.sha || '' }}`.
   The `== ''` form is NOT optional: `${{ inputs.base_url && '' || github.sha }}`
   looks equivalent and is wrong — '' is falsy, so it yields github.sha in both
   branches, and a base_url override would then assert against an unrelated
   environment's build.

RAILWAY_GIT_COMMIT_SHA — THREE PROBES, AND WHAT IS STILL UNVERIFIED
--------------------------------------------------------------------------
The brief flagged the COO's finding as one probe with a known blind spot. It
is, and the blind spot is real.

(a) COO, `list-variables` on the staging service: not listed. BLIND SPOT —
    that API enumerates user-set SERVICE variables. get-service-config's
    variableNames confirms the same 11 app variables (ALLOWED_ORIGINS,
    CLERK_*, DB_TYPE, HOST, NODE_ENV, OWNER_CLERK_ID, TURSO_*, VITE_*) and no
    platform-injected ones at all — including none of RAILWAY_PROJECT_ID,
    RAILWAY_SERVICE_ID etc., which Railway unquestionably does inject. So the
    listing's silence is expected behaviour, not evidence of absence.

(b) Railway docs (docs.railway.com/variables/reference): Railway provides its
    system variables "to all builds and deployments"; the Git variables table
    (RAILWAY_GIT_COMMIT_SHA among them) applies "if the deploy originated from
    a GitHub trigger".

(c) Empirical, and independent of (b): get-service-config shows
    source.repo = ryanv11/travel-tracker, branch main; and every staging
    deployment's Railway-side meta carries commitHash + branch:main. The
    precondition in (b) therefore holds for this service in fact, not just in
    principle.

VERDICT: (b) and (c) together make runtime injection EXPECTED. But none of the
three observes the deployed process's actual environment, and the staging
origin is firewall-blocked from this container, so runtime presence is
UNVERIFIED — stated as such rather than upgraded to a fact.

That is precisely why the baked-file layer was built rather than dismissed as
redundant. If the env var is present at runtime, layer 2 answers. If it is
present only at build time, layer 3 answers. If neither, /health says
"unknown" honestly and BUILD_COMMIT_SHA can be set by hand. The feature does
not depend on the unverified claim being true.
