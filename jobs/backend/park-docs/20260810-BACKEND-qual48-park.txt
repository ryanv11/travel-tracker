────────────────────────────────────────────────────────────────────
THE MECHANISM (read from node_modules, decisive)
────────────────────────────────────────────────────────────────────
@libsql/client lib-cjs/sqlite3.js:145-149 — transaction() hands the live
connection to the tx object and sets this.#db = null. The NEXT client query
calls #getDb(), sees null, and opens a NEW connection from #path:
  - :memory:  -> a brand-new EMPTY in-memory db (schema/data gone) -> throws
  - file:...  -> reopens the SAME file (committed data present) -> works
drizzle wraps this at drizzle-orm/libsql/session.cjs:85 and does NOT close the
tx connection after commit. Positive, self-verifying (code read) and it predicts
every runtime probe.

────────────────────────────────────────────────────────────────────
VERIFY-CHECKLIST VERDICTS (each with its probe)
────────────────────────────────────────────────────────────────────
1. file-backed tx + subsequent query survives — VERIFIED yes.
   Probe C (file:<tmp>): tx commits, subsequent SELECT = [{"c":1}], mid-tx
   unique violation rolls back whole tx (no orphan). Probe A (:memory:, same
   code, only URL differs): subsequent SELECT THROWS. Two probes fail
   differently; mechanism read is the third.

2. cheaper than file I/O? — VERIFIED a real alternative exists but is UNSAFE for
   the parallel suite (so NOT "file-backed is the only way").
   file::memory:?cache=shared works (probe D) with no file I/O, BUT all
   shared-cache in-memory clients in one process share ONE db (probe E: a
   separate client read another's table+row) and libSQL rejects a NAMED
   in-memory db to isolate them (probe F: mode= param rejected; also read the
   whitelist in @libsql/core config.js — in-memory mode whitelists only cache).
   Under Vitest fileParallelism:true (threaded pool) two files collide. Viable
   only with fileParallelism:false — its own cost. A @libsql/client version bump
   was NOT probed — marked UNVERIFIED (only pinned ^0.14.0 tested).

3. coexists with drizzle-kit patch + partial unique indexes — VERIFIED yes.
   drizzle-kit: grep -rn drizzle-kit src/ = comments only, never a runtime
   import; the test runtime builds schema via drizzle-orm/libsql/migrator, not
   the drizzle-kit CLI the patch governs; file-backed suite still built its
   schema through it and passed. Partial indexes: file-backed, a duplicate
   (osm_type,osm_id) is REJECTED by uniq_cities_osm_ref while TWO osm_id-NULL
   rows are BOTH allowed — proves the partial predicate is honoured, not a
   silently-full index (the false-green risk the brief named).

4. cost to 827-suite — VERIFIED passes, +~30% wall.
   :memory: baseline 52 files / 827 tests / 9.89s (tests 5.79s).
   file-backed 52 / 827 / 12.87s (tests 25.43s) — tests phase ~4.4x (per-test
   file I/O) but import/transform dominate wall, so observable +~3s.
   Revert re-run 827 / 10.01s — baseline restored. Blind spot noted: /tmp is
   likely tmpfs here; a real-disk CI runner could differ.

5. unblocks itemRepository.create atomic wrap — VERIFIED yes.
   create = base insert items.ts:148 + insertExtension:165 + a trailing
   fetchItemsWithExtensions (a SELECT AFTER the writes) — that trailing read is
   exactly what :memory: forbids under a transaction. Probe C models the write
   pair (rollback, no orphan) AND the post-tx read survives file-backed.
   executeCarryForward (items.service.ts:116) survives :memory: only because its
   route (places.ts:245) returns the tx result with NO post-tx query — accident
   of shape, cannot be copied by create.
