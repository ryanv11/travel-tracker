THREAD — BUG-30 (GitHub #154) — MERGED to main via PR #168
================================================================================

Bug: UK constituent countries (Scotland, England, Wales, Northern Ireland)
unavailable when adding a place. Root cause: GB was present in the countries
seed but with region_tier_enabled=0 — those four are ISO 3166-2 regions under
GB, not ISO 3166-1 countries themselves (GE-01/GE-02), so the Region tier
never surfaced for GB.

Deliverables (branch fix/bug30-uk-region-seed, merged):
  1. data/countries.json — GB row: region_tier_enabled 0->1,
     region_tier_label null -> 'Constituent Country'
  2. data/regions.json — added England/GB-ENG, Scotland/GB-SCT, Wales/GB-WLS,
     Northern Ireland/GB-NIR (real ISO 3166-2 codes, same shape as existing
     US/AU/CA rows)
  3. src/backend/migrations/0008_bug30_uk_region_seed.sql — data-only custom
     migration (drizzle-kit generate --custom; no DDL diff since
     region_tier_enabled/label and iso_3166_2 columns already exist from
     migration 0001). UPDATEs the GB countries row and INSERTs the 4 regions,
     guarded with `WHERE EXISTS (SELECT 1 FROM regions LIMIT 1)` so it is a
     no-op on fresh installs.
  4. src/backend/migrations/meta/_journal.json + 0008_snapshot.json —
     generated migration metadata. This is now the canonical idx-8 entry on
     main; BUG-33's migrations (below) were renumbered to 9/10 to avoid
     colliding with it.

IMPORTANT FINDING (self-caught, fixed before commit): first draft of the
region INSERTs used only a per-row NOT EXISTS guard with no check on whether
the table had been seeded at all — on a genuinely fresh install this would
have inserted the 4 GB rows into an empty regions table, tripping
seedRegions()'s "non-empty -> skip" idempotency guard and starving every new
install of the other 72 US/AU/CA regions. Fixed via
`WHERE EXISTS (SELECT 1 FROM regions LIMIT 1)`; verified against both a
from-scratch fresh-install simulation and the already-seeded dev.db path.

TOOLING NOTE (flagged, not blocking): drizzle-kit CLI `migrate` transiently
dropped a freshly-generated custom migration's journal entry on its first
run in that thread; not reproduced since. Possibly a 5th drizzle-kit@0.31.9
bug beyond the four tracked in patches/drizzle-kit+0.31.9.patch — worth a
closer look if it recurs.

THREAD — BUG-39 / ADL-36 carry-forward FK onDelete fix (2026-07-21) — branch
fix/bug39-carry-forward-fk-ondelete
================================================================================

Bug (GitHub #209): items.carriedFromItemId, a self-referencing FK
(`.references((): AnySQLiteColumn => items.id)`), had no onDelete clause.
@libsql/client enforces FKs by default (BUG-38), so the omission defaulted
to RESTRICT: DELETE /api/trips/:id (and direct item delete) 500'd whenever
one of the trip's items had ever been used as a carry-forward source for an
item on ANY other trip. Found by the WP-03/WP-04 Frontend brief (PR #208)
writing E2E coverage for the carried-forward tag; dispatched to Architect
for review before implementation per the schema-change-review rule.

Architect ruling: ADL-36 (jobs/architect/tech/20260307-architecture-
decisions-log.md) — onDelete: 'set null', not cascade (would destroy an
independent item on a different trip) or explicit restrict (the bug
itself). Full FK audit in the ADL confirmed BUG-39 is an isolated instance,
not a pattern — no other schema FK has the same "hard-deletable parent +
no onDelete + no app-level handling" shape.

Delivered (this thread, implementation only — Architect already decided):
  1. src/backend/db/schema.ts (~L432) — carriedFromItemId FK:
     .references((): AnySQLiteColumn => items.id, { onDelete: 'set null' }).

     db:generate (never db:push, ADL-15). SQLite can't alter a constraint
     in place, so drizzle-kit emitted the items table-recreation path
     (new table + copy + drop + rename + index rebuild) — exactly the path
     the committed drizzle-kit@0.31.9 patch guards. Eyeballed the SQL

     migration file document the R3 no-owner-at-migration-time caveat

     0000-0012). Read back the applied table SQL directly — FK cascade,

THE HAZARD, and why the mechanism differs from ADL-48 §8.1:
regions must NEVER be deleted and reloaded. cities.region_id REFERENCES
regions.id (schema.ts:101; migration 0000 line 23; confirmed at runtime via
PRAGMA foreign_key_list) and regions.id is AUTOINCREMENT (schema.ts:72;
migration 0000 line 145; confirmed in sqlite_master). A DELETE + reload
re-issues ids and repoints every existing city at a different subdivision,
or aborts under the FK enforcement asserted at boot. ADL-48 §8.1 defines
hash-gated seeding ONLY as DELETE + batch-insert and §11's S1 row invokes it
by name; §8.1's own safety argument is "nothing references gazetteer_cities",
which is false for regions. Both sections now carry a dated stamp saying so,
and the main ADL log entry carries an implementation-status block.

MECHANISM AS SHIPPED (src/backend/services/startup.service.ts):
  gate  — hash(bundled file) vs hash(table rows restricted to bundled codes).
          One SELECT of three columns, zero writes, ~3 ms. No stored hash and
          therefore no schema change: persisting one needs a meta table, and
          none exists (checked two ways — schema.ts sqliteTable exports, and
          every CREATE TABLE across all 16 migrations).
  write — INSERT ... ON CONFLICT (iso_3166_2) DO UPDATE SET name,
          country_code, updated_at, narrowed by drizzle setWhere to rows that
          genuinely differ. Chunked at 200 rows (600 params) so a single
          714-row statement cannot hit a conservative 999-parameter limit.
  DO UPDATE rather than DO NOTHING is for CONVERGENCE: under DO NOTHING a
  name correction leaves the hash permanently mismatched, so the seed would
  re-run every boot forever without ever fixing the row it keeps noticing.
  Rows present in the table but absent from the file are never deleted — one
  could already be referenced by a city.

WHY THE GATE HAD TO CHANGE: the old gate returned early on existingCount > 0.
Staging and production each hold exactly 76 regions (verified by the OP-27
review against the live tables), so a regenerated 714-row file would never
have applied to either. Same row-count trap that made BUG-30 need a
hand-written patch migration (0008_bug30_uk_region_seed.sql).
