THREAD — BUG-30 (GitHub #154) — MERGED to main via PR #168
================================================================================

Bug: UK constituent countries (Scotland, England, Wales, Northern Ireland)
unavailable when adding a place. Root cause: GB was present in the countries
seed but with region_tier_enabled=0 — those four are ISO 3166-2 regions under
GB, not ISO 3166-1 countries themselves (GE-01/GE-02), so the Region tier
never surfaced for GB.

Deliverables (branch fix/bug30-uk-region-seed, merged):
  1. data/countries.json — GB row: region_tier_enabled 0->1,
     region_tier_label null -> 'Constituent Country'
  2. data/regions.json — added England/GB-ENG, Scotland/GB-SCT, Wales/GB-WLS,
     Northern Ireland/GB-NIR (real ISO 3166-2 codes, same shape as existing
     US/AU/CA rows)
  3. src/backend/migrations/0008_bug30_uk_region_seed.sql — data-only custom
     migration (drizzle-kit generate --custom; no DDL diff since
     region_tier_enabled/label and iso_3166_2 columns already exist from
     migration 0001). UPDATEs the GB countries row and INSERTs the 4 regions,
     guarded with `WHERE EXISTS (SELECT 1 FROM regions LIMIT 1)` so it is a
     no-op on fresh installs.
  4. src/backend/migrations/meta/_journal.json + 0008_snapshot.json —
     generated migration metadata. This is now the canonical idx-8 entry on
     main; BUG-33's migrations (below) were renumbered to 9/10 to avoid
     colliding with it.

IMPORTANT FINDING (self-caught, fixed before commit): first draft of the
region INSERTs used only a per-row NOT EXISTS guard with no check on whether
the table had been seeded at all — on a genuinely fresh install this would
have inserted the 4 GB rows into an empty regions table, tripping
seedRegions()'s "non-empty -> skip" idempotency guard and starving every new
install of the other 72 US/AU/CA regions. Fixed via
`WHERE EXISTS (SELECT 1 FROM regions LIMIT 1)`; verified against both a
from-scratch fresh-install simulation and the already-seeded dev.db path.

TOOLING NOTE (flagged, not blocking): drizzle-kit CLI `migrate` transiently
dropped a freshly-generated custom migration's journal entry on its first
run in that thread; not reproduced since. Possibly a 5th drizzle-kit@0.31.9
bug beyond the four tracked in patches/drizzle-kit+0.31.9.patch — worth a
closer look if it recurs.

THREAD — BUG-33 schema half (GitHub #157, BRD GE-11) — PR #169
================================================================================

Problem: `cities` had no uniqueness constraint on (name, country_code) — the
find-or-create lookup path created a duplicate "Glasgow" row instead of
reusing the existing one (found in UAT 2026-07-20).

Delivered (branch fix/bug33-city-dedup-schema), originally at idx 8/9,
renumbered to idx 9/10 in the RENUMBERING THREAD below:
  1. src/backend/migrations/0009_bug33_dedupe_cities_data.sql — merges
     existing duplicate city rows (canonical = lowest id; geocode fields
     coalesced from the best-resolved duplicate). Re-points trip_places to
     canonical city; handles the case where that collides with
     uniq_trip_places_trip_city (two trip_places rows for one trip now
     targeting the same city) by keeping the earlier trip_place row and
     migrating items/activity-tags off the later one before deleting it —
     no user data lost.
  2. src/backend/migrations/0010_stiff_meltdown.sql (or regenerated tag) —
     adds UNIQUE(name COLLATE NOCASE, country_code) on cities (schema.ts:
     uniq_cities_name_country_ci).
  3. src/backend/db/schema.ts — cities table now has the unique index.

Approach reviewed with Architect before implementation (collation mechanism,
trip_places collision handling) per the no-schema-change-without-review rule.
Verified against the real dev.db duplicate data set (2x Glasgow/GB, 3x
Seattle/US, including one live trip_places collision) — cleanup output
matched expected merge exactly; unique index verified to block a
case-variant duplicate insert while allowing genuinely distinct cities.

NOT in this thread's scope: the find-or-create application logic that let
duplicates get created — that's Backend's parallel brief on
fix/bug33-city-dedup-logic. Backend's lookup WHERE clause needs to match the
new index's COLLATE NOCASE (ASCII-only case fold) or it will fail to find the
canonical row.
