1. VERIFIED db:seed needs no changes. It goes through getDb() exactly like
   everything else in the app — no filesystem-specific assumptions anywhere in
   src/backend/db/seed.ts. Confirmed idempotent: ran twice against a freshly
   migrated database, second run's onConflictDoNothing() left row counts
   unchanged.

2. VERIFIED db:migrate applies cleanly against a fresh, empty database. All
   11 migration files (0000 through 0010) applied in one pass, no errors.

3. FOUND AND FIXED a gap ADL-32 §9 didn't cover: drizzle.config.ts (used by
   drizzle-kit's own db:generate/db:migrate commands) is a SEPARATE connection
   from the app's runtime getDb() in db/index.ts. ADL-32 §9 only scoped
   "add authToken to createClient() in db/index.ts" to Backend — it said
   nothing about drizzle.config.ts, which drizzle-kit reads independently.
   Without a fix, db:migrate would have had no way to authenticate against a
   real Turso database, regardless of what Backend wires into db/index.ts.

   The fix needed two things, not one:
     a. TURSO_AUTH_TOKEN threaded into dbCredentials.
     b. dialect: 'turso' (not 'sqlite') for remote libsql:// URLs — confirmed
        by reading drizzle-kit's own Config type (node_modules/drizzle-kit/
        index.d.ts): the 'sqlite' dialect branch's dbCredentials type is
        `{ url: string }` only, no authToken field exists in that branch at
        all. Only the 'turso' dialect branch adds `authToken?: string`. This
        was caught by TypeScript failing to compile my first draft (authToken
        under dialect:'sqlite'), not by guesswork — I read the type
        definition to understand exactly why and fixed it properly rather
        than reaching for an `as any`.
     'turso' and 'sqlite' are otherwise the same SQL grammar (both libSQL) —
     this is a drizzle-kit config-surface distinction only, not a schema or
     ORM dialect change; does not touch ADL-25 (backend db typing stays
     LibSQLDb, confirmed by re-reading ADL-25's own reasoning before making
     this change).

   drizzle.config.ts now branches: dialect 'sqlite' + { url } for local
   file: URLs (unchanged behavior), dialect 'turso' + { url, authToken } for
   remote libsql:// URLs. Verified both branches directly: local file:
   migration still applies clean; a deliberately fake, unreachable libsql://
   URL with a dummy token correctly selected the turso dialect and attempted
   a real HTTP round-trip (got a 404 from the fake host, as expected — proves
   the auth token and turso wire protocol actually engaged, not silently
   skipped).

4. NEW SCRIPT: src/backend/db/reset-staging.ts, exposed as
   `npm run db:reset-staging`.
     - Dry run by default (prints per-table row counts, deletes nothing).
       --yes required to actually delete.
     - Clears all user-owned/trip data (items + 5 item-subtype tables,
       trip_places + its join table, trips + its 4 join tables, users) in
       explicit child-before-parent order via Drizzle's query builder — never
       raw/concatenated SQL (Shared Standard 21). Order is enforced
       explicitly rather than relying on SQLite's ON DELETE CASCADE actually
       firing, because whether libSQL enforces FK constraints (PRAGMA
       foreign_keys) is a connection-level setting this script doesn't
       control or want to assume.
     - Leaves countries/regions/cities untouched — reference/lookup data, not
       test cruft. countries/regions self-heal via startup.service.ts's
       idempotent seed-if-empty on every server boot; cities is deduplicated
       (BUG-33 unique index) and naturally bounded by real-world geography.
       users is intentionally NOT re-seeded after clearing — it self-heals on
       next sign-in via findOrCreateByClerkId (auth middleware), same
       self-healing pattern.
     - Re-seeds admin lists (trip_categories/activities/companions/
       map_shading_config) immediately after clearing, rather than waiting on
       the next Railway restart's auto-seed.
     - Safety guardrail: refuses to run against a remote (libsql:// or
       https://) URL unless it contains the substring "staging" — even with
       --yes. Documented as a blunt footgun-removal check, not a security
       control. --i-know-what-im-doing bypasses it. file: URLs (local dev)
       are exempt.
     - Functional-tested end to end: migrate -> seed -> insert a small
       user/trip/trip_place/item fixture -> reset --yes -> verified trip/user
       tables cleared, admin lists re-seeded, countries/cities left alone.
       Also tested the "staging" name guard both ways (fake prod-looking URL
       correctly refused; fake staging-looking URL correctly passed the guard
       and attempted a real connection).
