WHAT WAS BUILT
================================================================================

1. src/backend/db/schema.ts — companions: added userId (text, NOT NULL, FK
   -> users.id, onDelete: 'cascade'); UNIQUE changed from name-alone to
   uniqueIndex('uniq_companions_user_name').on(userId, name); added
   index('idx_companions_user').on(userId). Exact match to ADL-28's
   reference Drizzle definition.

2. src/backend/db/schema.ts — mapShadingConfig: added userId (same FK/
   cascade shape); PK changed from stateKey-alone to
   primaryKey({ columns: [stateKey, userId] }); added
   index('idx_map_shading_user').on(userId); kept the existing
   chk_map_shading_state_key CHECK constraint (all 6 state values) intact.

3. Migration 0012_grey_ultimates.sql — drizzle-kit's first-pass output was
   WRONG for both tables and required a hand rewrite (this is exactly what
   the brief warned could happen and told me to check for):
     - companions: drizzle emitted a bare `ALTER TABLE companions ADD
       user_id text NOT NULL REFERENCES users(id)` — no ON DELETE CASCADE,
       and no owner-backfill INSERT. This would fail outright applying
       against any dev.db with existing companion rows (SQLite refuses a
       NOT NULL ADD COLUMN with no DEFAULT on a non-empty table), and even
       on an empty table would have silently dropped the cascade behavior.
     - map_shading_config: drizzle DID choose table recreation (correct,
       since a PK change forces it) but its own generated INSERT...SELECT
       tried to read a "user_id" column FROM THE OLD map_shading_config
       table — which doesn't have one pre-migration. Would fail with
       "no such column: user_id" the moment it ran.
   Rewrote the file by hand: both tables now go through explicit __new_
   table recreation (PRAGMA foreign_keys=OFF/ON around each block,
   matching migration 0011's established style), each with the
   INSERT...SELECT...CROSS JOIN (SELECT id FROM users WHERE is_owner = 1
   LIMIT 1) owner-backfill pattern from ADL-28's reference SQL. Comments
   in the migration file document the R3 caveat (0 rows backfilled if no
   owner exists at migration time — accepted, dev-only scenario).

4. db:generate re-run after the hand-fix: "No schema changes, nothing to
   migrate" — confirms the snapshot/journal (which are derived from
   schema.ts's target state, not the literal SQL text) were never out of
   sync; only the SQL body needed correcting.

5. db:migrate applied clean against a fresh local dev.db — all 13
   migrations (0000-0012) in one pass. Read the applied table DDL straight
   from sqlite_master: FK cascade, composite PK, unique index, and CHECK
   constraint are all present exactly as specified.

6. Functional-tested the CORRECTED migration SQL against a hand-built
   pre-migration dataset (old shape: no userId columns) with 2 users (one
   is_owner=1, one not) and existing companions/shading rows. After
   applying: both companions and both shading rows landed on the OWNER's
   userId specifically — not the non-owner's, not left null. This is the
   one part of the ADL's design that's easy to get subtly wrong (e.g. by
   picking "a" user instead of "the" owner), so I didn't just trust the
   SQL shape, I ran it. Also verified 6 constraint behaviors directly
   against the migrated DB: cross-user same-name companion allowed,
   same-user duplicate name rejected (unique index), duplicate
   (state_key,user_id) rejected (composite PK), same state_key for a
   different user allowed, FK violation on a bogus user_id rejected, and
   cascade delete on user removal actually clears both companions and
   shading rows for that user. All 6 passed. Scratch files used for this
   were all outside the worktree/repo (scratchpad dir) and deleted after.

CONSEQUENTIAL FIXES — required to keep the brief's own verification bullets
green, not scope creep into repositories/routes/services
================================================================================

7. src/backend/db/seed.ts + src/backend/services/startup.service.ts — both
   used to globally seed companions and map_shading_config (at db:seed time
   and every server startup respectively). Post-ADL-28 there is no single
   global row set to seed any more: companions has no default list in the
   new per-user model, and shading config is lazily seeded per-user by the
   repository layer the Backend brief will add. Left as-is, these two
   files would not even compile (missing required userId in the insert
   shape) — and if compiled anyway (tsx doesn't type-check at runtime),
   the actual server would crash on every startup with a NOT NULL
   violation. Removed the companions/map_shading_config seed calls from
   both; trip_categories and activities (AD-09, unaffected by this ADL)
   still seed exactly as before. Documented the reasoning in both files'
   doc comments, citing ADL-28.

8. src/backend/db/reset-staging.ts — this ops script's whole framing
   (docstring + RESET_TABLES list) categorized companions/map_shading_config
   as global reference data, explicitly left untouched by a reset, and
   reseeded them globally after clearing trip/user data. Both tables are
   now user-owned data with ON DELETE CASCADE from users. Left unfixed,
   the script's own DELETE FROM users step would either orphan rows (if
   the remote libSQL connection doesn't enforce FK constraints) or hit a
   real FK violation (if it does) — precisely the ambiguity the script's
   own docstring says it doesn't want to rely on cascade to resolve. Moved
   both tables into RESET_TABLES in correct child-before-parent order
   (after trip_companions_map, before users), removed the now-invalid
   global reseed calls for both, and updated the docstring's "what is/
   isn't reset" section to match the new reality. Flagging this one
   explicitly: it's the one fix in this thread that goes beyond a
   mechanical schema-shape patch — it's a real ops-script correctness fix,
   made necessary by the FK I added. Happy to walk through the reasoning
   if COO or Backend wants to revisit the call.

9. Backend test suite — 5 files' hand-rolled in-memory DDL (companions/
   map_shading_config CREATE TABLE blocks, copy-pasted per test file
   rather than generated from schema.ts, an existing pattern predating
   this thread) hardcoded the old no-userId shape and broke at RUNTIME
   (not compile time — TS doesn't know the actual DB structure) once
   shading.service.ts or the admin companions route tried to touch a
   userId column that didn't exist in the test DB:
     - src/backend/repositories/__tests__/test-db.ts (shared factory —
       fixes trips.test.ts)
     - src/backend/routes/__tests__/owner-access.test.ts
     - src/backend/routes/__tests__/qa-backend-fixes.test.ts
     - src/backend/services/__tests__/shading.trip-countries.test.ts
     - src/backend/services/__tests__/shading.user-scope.test.ts
   Added userId column + FK (ON DELETE CASCADE) + updated unique index /
   composite PK to each, matching schema.ts exactly. Also added userId to
   2 insert fixtures that created companion rows directly (trips.test.ts,
   qa-backend-fixes.test.ts).

10. Two tests left genuinely broken by the same root cause, both marked

    owner-access.test.ts's "POST /api/admin/companions -> 201 for owner",
