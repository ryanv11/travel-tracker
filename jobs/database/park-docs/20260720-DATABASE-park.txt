================================================================================
DECISIONS MADE THIS THREAD
================================================================================

  DECISION: region_tier_label = "Constituent Country" for GB.
  REASON: BRD GE-02 says the tier "represents states, provinces, or
  territories depending on the country" but has no UK precedent; England/
  Scotland/Wales/Northern Ireland are officially termed "constituent
  countries" of the UK. Tracker's BUG-30 note already flagged this as the
  likely label ("region_tier_label likely 'Constituent Country'") — adopted
  as-is, no BRD language conflicts with it.
  ARCHITECT REVIEW NEEDED: No new table/column — region_tier_enabled and
  region_tier_label already exist and are exactly what GE-04/07 spec for
  per-country Region tier config. This is data only, not a schema change.

  DECISION: Guard the migration's region INSERTs with
  `WHERE EXISTS (SELECT 1 FROM regions LIMIT 1)`.
  REASON: See "IMPORTANT FINDING" in context/current.txt — an unconditional
  INSERT on a data-only migration would poison the "table empty = not yet
  seeded" invariant that startup.service.ts's seedRegions() idempotency guard
  relies on, permanently starving fresh installs of all 72 non-GB regions.
  Caught via a from-scratch fresh-install simulation before committing.

================================================================================
SCOPE
================================================================================

Brief: add a uniqueness constraint on cities(name, country_code) — case-
insensitive if it can be done cleanly at the DB level — plus a data-cleanup
migration for existing duplicates found in UAT ("Glasgow" appeared twice in
the place autocomplete). Explicitly NOT in scope: the find-or-create
application logic that let the duplicates get created — that's a parallel
Backend brief (fix/bug33-city-dedup-logic).

================================================================================
ARCHITECT REVIEW (pre-implementation)
================================================================================

Per the no-schema-change-without-Architect-review rule, consulted Architect
before writing any migration. Two open design questions and the ruling on
each:

1. Case-insensitivity mechanism — ruled: DB-level
   UNIQUE(name COLLATE NOCASE, country_code) as the hard guarantee (not
   backend-only normalization — that only prevents the bug from one call
   site, not from recurring via any other path), PLUS Backend's find-or-create
   read must match the same collation or it will fail to find the canonical
   row and attempt (and fail) an insert instead of reusing it. NOCASE's
   ASCII-only limitation (no Unicode/diacritic folding) is an accepted,
   documented tradeoff, not a silent gap.

2. Cleanup migration collision (two trip_places rows for the same trip
   colliding on the same canonical city_id, given uniq_trip_places_trip_city)
   — ruled: keep the earlier trip_place row, delete the later one, but
   re-point items.trip_place_id and merge trip_place_activities_map onto the
   survivor first — never lose booked items/notes as a side effect. Ruled
   this is a scoped one-time repair, NOT blocked by BRD OQ-05 (the open
   question about whether uniq_trip_places_trip_city should allow same-city
   revisits going forward) — OQ-05 is a forward-looking identity-model
   question; this migration works within today's constraint as it stands.

   Additional flags from Architect, both incorporated: canonical row keeps
   lowest id, but geocode fields (lat/long/status/attempted_at) are coalesced
   from the best-resolved duplicate in the group if canonical isn't already
   resolved; region_id divergence between duplicates should not be silently
   picked — implemented as a NULL-fill only (never overwrites a non-null
   value), so genuine divergence surfaces rather than getting erased.

================================================================================
WHAT WAS BUILT
================================================================================

1. src/backend/migrations/0008_bug33_dedupe_cities_data.sql (custom migration,
   via `drizzle-kit generate --custom`)
   - Maps every city to its duplicate-group canonical id (lower(name),
     country_code; canonical = MIN(id)).
   - Coalesces geocode fields onto canonical from the best-resolved duplicate.
   - Computes, per (trip_id, canonical city_id), which trip_place row
     survives (MIN(id)) — covers every trip_place row, not just ones sitting
     on a duplicate city, since a trip may already have a row on the
     canonical city that a duplicate's row will now collide with.
   - Re-points items.trip_place_id and merges trip_place_activities_map from
     losing trip_place rows onto the survivor (INSERT OR IGNORE against the
     composite PK to skip already-present activity tags).
   - Deletes losing trip_place rows, re-points surviving trip_places.city_id
     to canonical, deletes the now-unreferenced duplicate city rows.

2. src/backend/migrations/0009_stiff_meltdown.sql (schema diff via
   `drizzle-kit generate`)
   - CREATE UNIQUE INDEX uniq_cities_name_country_ci ON cities
     (name COLLATE NOCASE, country_code)

3. src/backend/db/schema.ts — cities table (t) => [...] array: added the
   uniqueIndex entry with an inline comment on the NOCASE tradeoff and the
   note that Backend's lookup must match the collation.

BUGS DISCOVERED
================================================================================

None beyond BUG-33 itself. Noted but not investigated further: no
`PRAGMA foreign_keys = ON` anywhere in src/backend/db/index.ts, so declared
`onDelete: 'cascade'` FKs (e.g. trip_place_activities_map -> trip_places) are
not actually enforced at the SQLite engine level today — this is why the
cleanup migration explicitly re-points/deletes child rows itself rather than
relying on cascade. Not fixing this pre-existing condition here (out of
scope for BUG-33), but flagging it since it means ANY manual DELETE against a
parent row in this codebase can silently orphan children rather than erroring
or cascading. Worth an Architect/Backend look if it hasn't already been
raised elsewhere.
