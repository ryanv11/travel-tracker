THE DECISION IN ONE LINE
------------------------
Staging keeps watching `main` (continuous soak). Production is repointed to watch a long-lived
`production` branch, promoted by explicit `git merge --ff-only origin/main` + push. Three rings:
staging (main) / production (production branch) / preview (per-PR, orthogonal, ADL-32 §5).

WHY BRANCH, NOT TAGS / NOT A GH ACTION
--------------------------------------
Railway watches BRANCHES first-class → zero deploy glue for both envs. ADL-32 picked Railway
specifically to avoid hand-rolled deploy steps; a tag/API-triggered prod deploy would put that
glue right back. Fast-forward-only makes an unsoaked commit in prod structurally impossible
(every production commit is an ancestor of main). `production` ref = "what's live"; `git log
production..main` = "what's about to ship". Tags kept only as an OPTIONAL release marker.

CI GATE INTERACTION (the neat property)
---------------------------------------
Railway's CI-gated-deploy is unchanged and layers underneath. GitHub check-runs key on the
commit SHA, not the branch — so a fast-forward carries the commit's already-green checks from
main. Railway's gate sees green immediately: no redundant CI run, gate still honoured. DO NOT
add a `push:[production]` trigger to CI workflows (would re-run CI pointlessly).

BRANCH-PER-BRIEF: EXPLICITLY UNCHANGED (§7)
-------------------------------------------
feat/fix/chore still branch off main, PR to main, COO squash-merges. `production` is NEVER a
PR target, never gets direct commits, never branched from. Agents never touch it — COO/PO-only,
same authority boundary as merge. A feat/* off production would be a mistake, not a pattern.
