────────────────────────────────────────────────────────────────────────
THE ONE THING TO CARRY FORWARD IF NOTHING ELSE
────────────────────────────────────────────────────────────────────────
The design changes the key rows are WRITTEN with and leaves the key rows are READ by
unchanged. findOrUpgradeCity step 1 (cities.ts:176-187) keeps matching on
(name COLLATE NOCASE, country_code, COALESCE(region_id,0)) and that query is what actually
decides which city a user gets. Every HIGH finding is a consequence of that split.

Corollary worth remembering beyond this defect: on this route, pass 1 short-circuits with a
200 BEFORE the geocoder is consulted (cities.ts:299 vs :312). Any design that fixes something
inside resolveCityName/classifyCandidates has to say what pass 1 does first, or the fix is
unreachable for every name that already has a row.

METHOD — WHAT MADE THE DIFFERENCE
────────────────────────────────────────────────────────────────────────
The previous round's fatal flaw was describing cities.ts rather than running it. Two harnesses
did all the work here and both are cheap to rebuild:

1. Route-level: copy the cities.f1f2-ruling.test.ts pattern. It mocks ONLY nominatim-client.js,
   so findOrUpgradeCity, classifyCandidates and resolveCity all execute for real against a
   migration-built libSQL DB. Trick that avoided editing source: to test the post-D4-fix world,
   feed a candidate set TODAY's classifier already calls 'ambiguous' — the route takes exactly
   the step-4c path the proposed fix would force.
2. DDL-level: build the proposed indexes in a plain @libsql/client :memory: DB and drive them
   with the SHIPPED query text copied verbatim out of cities.ts — not a paraphrase. That is what
   exposed F4 (arbitrary pick) and F9 (the design's own EXPLAIN was of a different query).
   Note: run scratch .mjs from inside the worktree, not the scratchpad — @libsql/client resolves
   from node_modules.

────────────────────────────────────────────────────────────────────────
THE RECOMMENDATION THE COO ACTUALLY NEEDS
────────────────────────────────────────────────────────────────────────
INVERT THE STAGING. The design ranks D8 (the user-choice channel) fourth and Medium-confidence
and calls it "the least load-bearing decision here." It is the prerequisite. Once the user can
choose, the classifier can be strict with NO calibrated threshold at all:

  "Ambiguity is not a property of the candidate set — it is the absence of a user decision."

The geocoding.service.ts:97-102 objection (counting hits marks everything ambiguous) is entirely
conditional on there being no channel to ask. With a channel it costs one tap.

And the further reframe to put to the PO before S3/S5 is briefed: this is a PRODUCT question in a
data-model costume. Three designs have asked "what key makes two Newports different rows?" The BRD
asks "what is the user shown before anything is written?" GE-16's answer to four Newports is not
four rows — it is one question.
