3. THE SINGLE MOST IMPORTANT THING TO CARRY FORWARD
================================================================================
Three HIGH findings converge on one clause and are fixed by ONE change:

  MAKE THE CONFIDENCE ENUM THREE-VALUED.
  'confirmed' | 'suggested' | 'ambiguous' | 'none', not 'confirmed'-or-null.

  - Complete + attributed + unanimous     -> 'confirmed', fill silently (GE-15)
  - INCOMPLETE but UNDIVIDED              -> 'suggested', FILL + visible chip
                                             (UX spec §3.2, GE-16-safe)
  - Divided (optionsLength > 1)           -> 'ambiguous', blank + ask (GE-16;
                                             this is BUG-71's actual case)
  - No information                        -> 'none', blank + "couldn't determine"

This does NOT reintroduce BUG-71 — Springfield's region set is divided, so it
stays blank either way. The ONLY case that moves is undivided-but-incomplete,
which the ruling blanks and this suggests. It costs one enum member.

Why it matters: it simultaneously closes F1 (the UX-spec conflict), F2 (the
never-helps regression) and F3 (the false robustness claim), and it SHRINKS the
GE-15 amendment §8 asks for rather than growing it.

================================================================================
HIGH — F1: The ruling's "confirmed or null" CONTRADICTS the merged UX spec.
  UX §3.2: "the country field is never auto-committed without the user seeing
  and confirming it as a suggestion… render it as a visibly tentative default…
  Suggested: France — from 'Rome'". UX §10 makes it a success criterion. UX
  §12.2 item 3 keeps it explicitly IN MVP scope. The ruling's §10 table says it
  "adopts, does not re-specify" the UX spec — it defers to §3.3 (region) and
  never reads §3.2 (country), which decides the exact question B1 decides, the
  other way. Consequence: the §7.3 Frontend brief is self-contradictory as
  written. Lifecycle rule 2 stamp on UX §3.2/§10 is also outstanding.

HIGH — F2: truncation vetoes the COUNTRY too, on a raw count inflated by noise.
  The ruling is RIGHT that truncation must be measured on the raw array (the
  soundness argument is correct). It never draws the consequence: `data` counts
  streets, hotels, townships — so the withhold rate tracks OSM NOISE DENSITY,
  not name ambiguity, and the truncation flag fights the settlement filter.
  Categories worked through in review §3.1. Denver/Paris/London plausibly go
  blank where they auto-fill correctly today. 10->40 helps but is the CEILING of
  the wrong lever (40 believed max). Better lever: featuretype=settlement /
  layer=address on the DISCOVERY CALL ONLY — free, same request, makes raw count
  actually mean "settlements named X". MARKED UNVERIFIED with a named probe; I
  am asking it be probed, not adopted blind.

HIGH — F3: §3.2's robustness claim is false on both halves.
  "Can only fail toward a right answer" excludes "no answer" from failure by
  fiat — the same absence-vs-evidence move the ruling diagnoses one section
  earlier, inverted. "Without knowing a single fact about the live payload"
  depends on exactly ONE fact: that Nominatim returns >= limit rows whenever
  more matches exist. If dedupe or an importance cutoff can return 6 rows at
  limit=40 while the index holds hundreds, truncated=false and a unanimous 6
  auto-fills Virginia — BUG-71 reproduced through the fix meant to prevent it.

MEDIUM — F4: a Nominatim outage is indistinguishable from a no-match.
  geocode.ts collapses status:'error'/'disabled' into empty candidates + HTTP
  200, so lookupCityCountry sees failed:false and BUG-73's banner never fires.
  BUG-73 covers the browser<->backend hop ONLY, not backend<->Nominatim — this
  is PRE-EXISTING (not caused by the ruling) but §7.3's mapping makes it
  user-visible and actively wrong ("we couldn't confirm" when we never asked).
  Fix: confidence.lookup: 'answered'|'failed'|'disabled', routed into BUG-73's
  existing, already-tested amber banner + Retry.
