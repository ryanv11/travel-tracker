5. THE CALLS MOST WORTH CHALLENGING (and I want them challenged)
================================================================================
5.1 D5's CONTAINMENT RULE — the weakest thing in the deliverable.
    Design: the backend resolves the city name against the geocoder FIRST and builds the row
    from the canonical response, re-running find-or-create against THAT name. This is what
    actually buys "cased normalised matching, lookup against a service": case-folding alone
    (today's COLLATE NOCASE + uniq_cities_name_country_ci) converges "denver"/"Denver" and
    NOTHING ELSE — not "Denverr", not "denver co", not "Zurich"/"Zürich" (the schema comment
    already documents COLLATE NOCASE as an ASCII-only fold). Canonical-name matching converges
    all of them.

    Then the contested part: a row is GLOBALLY VISIBLE once geocode_status='resolved'; while
    'pending' it is visible only to its creator. Costs one nullable cities.created_by_user_id
    and one WHERE clause. Promotion is ALREADY automatic and ALREADY server-side (processQueue
    every 15 min), so a legitimate offline-created city goes global by itself and a junk name
    like "asdf" never resolves and so never goes global. Self-maintaining, no moderation
    queue, never blocks the user.

    THE OBJECTION: that is MY reading of "auto create goes global but do some validation" —
    global WHEN validated. A reader who takes it as "global immediately, owner curates after"
    is not misreading it, and that is simpler and needs no column. Flagged to the COO as a
    PO-confirmable question (Q-B), not settled by me.

5.2 D9's PHASE 1/2 GAP. Phase 1 opens city creation before Phase 2 supplies its validation
    authority. Defensible — the P1 is a live, total outage for non-owners, and find-or-create,
    the unique index, country/region validation and the .strict() schema all hold regardless,
    with coordinates server-only either way. But it is a deliberate temporary weakening and
    should be challenged if the reviewer thinks the phases should merge. My recommendation:
    dispatch Phases 1 and 2 together IF capacity allows; the gap is pure downside if avoidable.

5.3 WHY THE PER-USER PATTERN IS RIGHT FOR CATEGORIES AND WRONG FOR CITIES. Both are shared
    lists; I moved one and refused to move the other, so the discriminator needs to be
    explicit. A CATEGORY is a taxonomy choice — no external truth condition, no convergence
    property; two users adding "Beach" and "Beach Holiday" produce two rows both of which are
    correct. A CITY is a fact about the world — a geocoder resolves it or does not, and the DB
    already enforces a natural uniqueness key; two users adding "Denver, US" CONVERGE ON ONE
    ROW by construction. Per-user cities would fragment the join key behind carry-forward
    (BUG-33), city item history, LB-01 aggregation and city shading aggregates. This is the
    one place I would push back hardest.

13.1 D10 — CLASSIFY THE FAILURE, DON'T JUST COUNT IT.
     The COO's instruction was an attempts cap. The PO refined it: retry integration and
     network errors; a NO-MATCH response should never be retried. The refinement is
     better — a pure cap still burns N attempts on every "asdf".
     THE FINDING THAT MADE IT CHEAP: the distinction already exists in the code and is
     thrown away. resolveCity has FOUR distinct failure branches — isOnline false (:85),
     !resp.ok (:107-110), !data.length (:115-119), catch (:137-140) — and all four
     return false leaving the row 'pending'. The terminal one even carries the comment
     "No results — leave as pending, will retry on next queue run". The information is
     available at the branch point; only the persistence is missing. This is a POSITIVE
     finding (the branches are there to read), not an absence claim.
     DESIGN: new geocode_status 'unresolvable' for terminal; geocode_attempts counter for
     recoverable, to a cap. Rejected a boolean flag (duplicate state machine — section
     4.5 rejects a second one on exactly these grounds) and an attempts-sentinel (loses
     the semantic distinction the PO drew). DECISIVE PRACTICAL ARGUMENT: the partial
     index idx_cities_geocode WHERE geocode_status='pending' automatically stops indexing
     dead rows ONLY if terminal is a status value.
     CRITICAL DETAIL: isOnline()-false and GEOCODING_ENABLED=false must NOT increment —
     they are GLOBAL conditions, not per-city failures. Counting them means one offline
     weekend burns every pending city's budget and they all fall out of the queue
     permanently. processQueue returns early on both, but resolveCity is ALSO called
     directly from POST /api/cities.
     COST CHANGE, REPORTED BECAUSE THE COO ASKED: amending chk_cities_geocode_status is a
     SQLite table recreation. S4 stops being a cheap ADD COLUMN. THE RELEASE NOW CARRIES
     THREE TABLE RECREATIONS, NOT TWO. cities is the fiddliest of the three — a PARTIAL
     index and a COLLATE NOCASE EXPRESSION index, which are two of the four drizzle-kit
     bug classes ADL-15 patches. Only one inbound FK (trip_places.cityId), so the blast

13.2 D11 — THE CORRECTION PATH, AND WHY I PUT IT AT THE PLACE LEVEL.
     The release CREATES the trap: containment (4.4) plus a terminal state (D10) means a
     user who types "Denvr" owns a row that is invisible, never retried, and — today —
     uneditable and undeletable by them. A release that creates a trap must ship its
     escape. Agreed with the COO on that without reservation.
     FACTS ESTABLISHED FIRST, because they narrowed the design sharply:
       - PATCH /api/cities/:id is owner-only (:223/:225) and its schema accepts ONLY
         region_id — it cannot repair a name even for the owner.
       - There is NO DELETE route on cities (my probe: six routes, four GET one POST one
         PATCH; the COO independently ran three more).
       - trip_places.cityId is .notNull() with NO onDelete, so a city cannot be deleted
         while a place references it — and in the typo case the place always exists.
         DELETE DOES NOT SOLVE THE REPORTED SCENARIO.
       - AND ONE MORE THAT RESHAPED THE ANSWER: city_id is CREATE-ONLY on places.
         UpdatePlaceDatesSchema is .strict() with only dates. So the only escape today is
         deleting the place and re-adding — WHICH DESTROYS ITS ITEMS AND ACTIVITY TAGS,
         since both hang off trip_place_id.
     DECISION: make city_id updatable on a place. Correction becomes "this place is in
     the wrong city", re-selected through the existing AddPlaceFlow. Chosen over opening
     PATCH /api/cities to the creator because:
       (a) NO UNIQUENESS-COLLISION CASE. Editing Denvr to Denver when Denver already
           exists violates uniq_cities_name_country_ci, and the natural repair IS
           re-pointing — so the city-edit path needs this operation anyway.
       (b) PRESERVES THE USER'S WORK — items and activity tags survive.
       (c) NEVER WRITES TO A SHARED GLOBAL ROW. A pending city is NOT private: review P2
           established a second user posting the same name gets the first user's row back.
           So a creator-edit path can silently mutate a row another user depends on.
       (d) Keeps D1 clean — no write delegation on tier-1 data.
     DELETE-AND-RE-ADD ALREADY WORKS AND NEEDS ZERO BUILD (places.ts:112 plus the ordinary
     create flow). Worth stating plainly — it had been framed as blocked and it is not.
     WHERE I DISAGREED WITH THE COO ON TIMING: the orphan-cleanup hook. Agreed the shape
     is right (a hook inside place removal, not a public DELETE route). Disagreed on the

     a three-way prompt — two of whose branches don't delete the place at all. Briefing it
     now designs against a flow about to change. Deferred with the full predicate written

     FRAMING PUSHBACK: the COO proposed a tier transition (per-user while unresolved,
     global once resolved) and asked whether D1 should say so. I said no. A pending city

13.3 D12 — WRONG MATCHES. The PO's sharpest question of the round.
     Containment gates on 'pending', so it protects against cities that NEVER resolve and
     does nothing about cities that resolve to the WRONG place — likelier AND worse,
     because 'resolved' bypasses containment and enters the shared catalogue as
     authoritative on first write.
     THE MINIMUM, AND IT IS CHEAP BECAUSE THE DATA IS ALREADY THERE: CreateCitySchema
     already REQUIRES country_code and accepts region_id, while resolveCity sends a bare
     q string with the country NAME appended and no filter (:97-103). THE BACKEND ALREADY
     HOLDS THE DISAMBIGUATING ANSWER AND DOES NOT USE IT. Four rules:
       1. Pass Nominatim's countrycodes= filter from the validated country_code. This
          alone removes the London-UK-vs-Ontario and Cambridge-UK-vs-Massachusetts classes.
       2. Disambiguate by region_id where the user gave one.
       3. USER SELECTION IS AUTHORITATIVE — the lookup may supply coordinates and a
          canonical name, never override a country or region the user explicitly chose.
          (Answering the who-wins question directly: the user has ground truth about where
          they went; the geocoder has a ranked guess; country_code is already validated
          against our own countries table.)
       4. Ambiguity surviving 1-3 creates 'pending' rather than picking first. Deliberately
          narrow — WITHOUT step 1 a plain ambiguity-block would leave "London" permanently

     DECLINED A FOURTH STATUS. Separating "the geocoder answered" from "fit for the shared

D13 — CITY IDENTITY (PO pulled into scope; I had deferred it, which was the mistake in its
  purest form). Identity becomes (name COLLATE NOCASE, country_code, COALESCE(region_id, 0)).
  THE SENTINEL IS THE WHOLE DESIGN. region_id is nullable and SQLite treats NULLs as distinct
  in a unique index, so the naive UNIQUE(name, country, region_id) permits UNLIMITED
  duplicates for every non-region-tier country — re-opening BUG-33. COALESCE collapses NULL
  to 0; 0 is safe because regions.id is AUTOINCREMENT, which starts at 1 and never issues 0
  (verified, not assumed).
  TWO PROPERTIES THAT MAKE IT MUCH SAFER THAN IT SOUNDS, both worth carrying forward:
    1. The new key is STRICTLY MORE PERMISSIVE than the one it replaces — adding a column to
       a unique key can only permit more rows — so NO EXISTING ROW CAN VIOLATE IT. No
       backfill, no conflict handling, no data risk in the migration.
    2. region_id MUST be NULL when region_tier_enabled=0 (cities.ts:106-108), so for those
       countries COALESCE is invariantly 0 and the index degenerates to today's
       (name, country_code). The BUG-33 guarantee is preserved EXACTLY where it matters.
  THE RISKY HALF IS THE LOOKUP, NOT THE INDEX — and I said so in section 13, because the
  reviewer will otherwise aim at the DDL. cities.ts:126-130 becomes three steps: exact match
  on the region key; then WILDCARD-UPGRADE — if the request carries a region and a row exists
  with the same name/country and region IS NULL, ADOPT it by setting its region rather than
  inserting; then insert. A region-less row is an UNDER-SPECIFIED record, not a different
  city. Omit that middle step and the system starts creating duplicates — BUG-33 through the
  front door.
  THE REVERSE CASE HAS NO SAFE AUTOMATIC ANSWER: no region supplied while several same-name
  rows exist. Routed to D14 rather than guessed. Where exactly one row matches name+country
  and no region is given, return it — today's behaviour, no regression.
  MIGRATION COST: ABSORBED. The index change lands inside the cities recreation D10 already
  forces. No fourth migration.

D14 — MULTI-RESULT: ASK, THROUGH THE CONTROL THAT ALREADY EXISTS. Zero candidates create
