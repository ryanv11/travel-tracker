5. THE CALLS MOST WORTH CHALLENGING (and I want them challenged)
================================================================================
5.1 D5's CONTAINMENT RULE — the weakest thing in the deliverable.
    Design: the backend resolves the city name against the geocoder FIRST and builds the row
    from the canonical response, re-running find-or-create against THAT name. This is what
    actually buys "cased normalised matching, lookup against a service": case-folding alone
    (today's COLLATE NOCASE + uniq_cities_name_country_ci) converges "denver"/"Denver" and
    NOTHING ELSE — not "Denverr", not "denver co", not "Zurich"/"Zürich" (the schema comment
    already documents COLLATE NOCASE as an ASCII-only fold). Canonical-name matching converges
    all of them.

    Then the contested part: a row is GLOBALLY VISIBLE once geocode_status='resolved'; while
    'pending' it is visible only to its creator. Costs one nullable cities.created_by_user_id
    and one WHERE clause. Promotion is ALREADY automatic and ALREADY server-side (processQueue
    every 15 min), so a legitimate offline-created city goes global by itself and a junk name
    like "asdf" never resolves and so never goes global. Self-maintaining, no moderation
    queue, never blocks the user.

    THE OBJECTION: that is MY reading of "auto create goes global but do some validation" —
    global WHEN validated. A reader who takes it as "global immediately, owner curates after"
    is not misreading it, and that is simpler and needs no column. Flagged to the COO as a
    PO-confirmable question (Q-B), not settled by me.

5.2 D9's PHASE 1/2 GAP. Phase 1 opens city creation before Phase 2 supplies its validation
    authority. Defensible — the P1 is a live, total outage for non-owners, and find-or-create,
    the unique index, country/region validation and the .strict() schema all hold regardless,
    with coordinates server-only either way. But it is a deliberate temporary weakening and
    should be challenged if the reviewer thinks the phases should merge. My recommendation:
    dispatch Phases 1 and 2 together IF capacity allows; the gap is pure downside if avoidable.

5.3 WHY THE PER-USER PATTERN IS RIGHT FOR CATEGORIES AND WRONG FOR CITIES. Both are shared
    lists; I moved one and refused to move the other, so the discriminator needs to be
    explicit. A CATEGORY is a taxonomy choice — no external truth condition, no convergence
    property; two users adding "Beach" and "Beach Holiday" produce two rows both of which are
    correct. A CITY is a fact about the world — a geocoder resolves it or does not, and the DB
    already enforces a natural uniqueness key; two users adding "Denver, US" CONVERGE ON ONE
    ROW by construction. Per-user cities would fragment the join key behind carry-forward
    (BUG-33), city item history, LB-01 aggregation and city shading aggregates. This is the
    one place I would push back hardest.

6. FINDINGS EN ROUTE — not fixed, spec-only scope
================================================================================
 1. A PREMISE IN THE DIRECTION IS WRONG, AND CORRECTING IT SHRINKS THE WORK.
    The direction states the pending/resolve machinery "is currently driven from the browser,
    which is the same architectural problem BUG-55 exposes." It is not.
      Probe 1: useGeocodeRetryQueue.ts's only network call is apiGet('/api/cities/:id'), and
               its header comment says so — "Polling is read-only (BUG-29) — the backend
               re-runs geocoding itself every 15 minutes."
      Probe 2: processQueue (geocoding.service.ts:148-192, "Called on startup and every 15
               minutes") is imported and invoked by server.ts:47.
    They fail differently: (1) misses a second frontend geocoding call, (2) misses the queue
    being invoked from elsewhere. Both agree. The ONLY browser-driven geocoding in the app is
    lookupCityCountry — the BUG-55 path, nothing else. The retry architecture is already
    correct. Phase 2 replaces one function, not a subsystem.

 2. STALE it.skip SUPPRESSING A LIVE ASSERTION. security.access-matrix.test.ts:457 skips
    'PATCH /api/cities/1 -> 403' pending BUG-22. BUG-22 HAS merged — requireOwner is present
    at cities.ts:211. The skip hides an assertion D4 makes load-bearing: city CURATION staying
    owner-only is precisely what makes opening city CREATION acceptable. Unskip in Phase 1.

 3. PHASE 3'S MIGRATION MUST PRESERVE `id` THROUGH THE CROSS JOIN. trip_categories_map
    (schema.ts:273) FKs to trip_categories.id, so existing mappings die if ids are regenerated.
    ADL-28's companions migration already does this correctly — prior art to copy, not
    re-derive.

 4. BLOCKING PRE-MIGRATION CHECK, and an honest limit on my own reasoning. I expect NO
    non-owner holds category/activity assignments (the picker has always 403'd, so it has
    always rendered empty), which would make the owner-backfill nearly a no-op. That is an
    INFERENCE FROM THE UI PATH, NOT A VERIFIED FACT, and it has a named blind spot: POST/PATCH
    /api/trips accepts category_ids and activity_ids directly under requireAuth alone, so a
    non-owner COULD have assigned them outside the UI. The Database brief must query staging
    (scripts/agent-diagnostics/turso-query.mjs) before migrating, not migrate on my inference.

 5. ODbL ATTRIBUTION GAP — SINGLE PROBE, FLAGGED AS SUCH. ADL-43 §6.2 established that ODbL
    attribution on sourced data is "a real obligation, not a formality." Nominatim results are
    OSM-derived, the app already stores Nominatim coordinates, and D5 increases reliance by
    storing service-derived canonical NAMES too. README.md:18 names Nominatim as a stack
    component; my grep for "attribution"/"ODbL" in README.md found nothing. I checked ONLY
    README.md — LICENSE, a UI footer, or the map attribution control could carry it. Verify
    before acting. Recommend a small COO tracker item, per ADL-43's Natural Earth model. Not a
    blocker and not mine to fix here.

 6. /api/admin/{categories,activities}/active is a misnomer for the Phase 1 window — an
    "admin" URL any authenticated user reads. Deliberately accepted because Phase 3 moves the
    resource to /api/categories + /api/activities and DELETES the carve-out. Scaffolding, not
    design — and the FAIL-CLOSED comment block must say so, or a later reader will treat it as
    permanent.

7. PROBES RUN — negative-findings discipline
================================================================================
Every absence claim in the deliverable carries two probes that fail differently, or is marked.

 * "AD-09's any-user-can-create was never built":
     (1) structural read of admin.ts — the CRUD factory's mounts (232-233) sit below the
         requireOwner guard (105);
     (2) grep -rn "tripCategories|activities" src/backend --include="*.ts" — writes appear
         ONLY in that factory and in db/seed.ts (startup seeding, not a route).
     Fails differently: (1) misses a handler on a differently-named router — exactly the
     assumption behind this project's earlier false "no router.delete in trips.ts" claim;
     (2) misses a write that never names the table symbol. Independently corroborated by
     ADL-28 Question 5, which recorded the same thing from the other direction.

 * "categories/activities have no per-user column":
     (1) table definitions at schema.ts:141-167 (id, name, is_active, created_at, updated_at);
     (2) absence of userId in createAdminListRouter's serializer (admin.ts:113-131), which
         returns the full row shape.
     This probe is what turned up the global UNIQUE(name) that makes Phase 3 a table rebuild.

 * "the geocode retry path is browser-driven" (a claim I DISPROVED — see 6.1): two probes.

 * "Nominatim is unreachable from this devcontainer" (ENV-01 — RE-PROBED, not inherited from
   the tracker note, since age is not evidence):
     (1) curl https://nominatim.openstreetmap.org/... -> exit 7;
     (2) curl https://api.github.com -> 200 FROM THE SAME SHELL as a control, plus CLAUDE.md's
         documented allowlist.
     The control is the load-bearing half: without it, exit 7 is equally consistent with the
     network simply being down — which is the shape of the false "firewall reaches no Turso
     host" claim this project already paid for.

 * "README carries no ODbL attribution": ONE probe only, explicitly marked UNVERIFIED in both
   the standalone doc §4.6 and item 6.5 above, with the blind spot named.
