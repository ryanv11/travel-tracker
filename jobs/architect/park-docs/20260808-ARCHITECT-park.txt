THE ONE THING TO CARRY FORWARD
------------------------------
I did NOT inherit the brief's "~65 unsafe sites, build one chokepoint" frame. Two probes
(grep count + per-file/per-predicate breakdown) show the 65 is exact but mostly benign — only
4 inline eq(userId) predicates in route handlers; the rest pass req.user!.id into repositories
that already scope (OP-06 §5.2/§5.3 = PASS). The honest problem is three-fold: the filter is
(a) not DRY, (b) not enforced, (c) not universal (cities.ts has no repo). And cities are GLOBAL
data (schema.ts:113-121) — so citiesRepository is a consolidation/testability/BUG-87-seam move,
NOT a cross-tenant fix. Getting that precise matters: framing cities as user-owned would send QA
to write vacuous cross-tenant tests on a global table (the QUAL-22 trap). This is the
"question the frame" rule applied by the author, for once, not the PO.

THE LOAD-BEARING ENGINEERING CALL (D2)
--------------------------------------
"Structurally impossible" is too expensive in TypeScript+Drizzle — I considered a typed
pre-filtered builder, a branded row type, and a runtime SQL assertion, and rejected all three as
PRIMARY (they fight .where()-replaces-not-appends / $dynamic() / joins, or guard the wrong point).
The correct posture is defence-in-depth (OP-06 §5.5's own doctrine): routes call getDb() ZERO
times (fail-closed grep guard removes the route-level class entirely) + scopeToUser makes the
repo filter a one-line review + an ATDD cross-tenant matrix at every user-data route is the
regression net. If the reviewer/PO pushes for "impossible", that is the tradeoff to re-litigate —
but I believe caught-with-3-layers is genuinely stronger than a rewrite-plus-theatre.
