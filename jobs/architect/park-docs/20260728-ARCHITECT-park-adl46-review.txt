3. THE METHOD NOTE THAT IS WORTH KEEPING
================================================================================
Both blocking findings came from EXECUTING rather than reading.

F2 in particular: section 9.3's premise ("UNIQUE(name) -> UNIQUE(user_id, name)
cannot be done with ALTER TABLE, so this is a table recreation") is plausible,
carefully written, and consistent with SQLite's documented limits. It is still
wrong for this schema, because the unique is realised as a standalone index.
Nothing short of running db:generate would have caught it — and the generated
file then failed to apply at all. Rule worth carrying: WHERE A SPEC ASSERTS WHAT
A TOOL WILL EMIT, RUN THE TOOL.

Second, smaller: the review target the author named as highest-risk (the section
3.3 data assumption) was sound, and the target they named as settled-and-safe
(the migration shape) was where the real error sat — one step upstream of where
they were looking. Aiming a review at the author's own confidence register is
useful but not sufficient.

6. PO CONSTRAINT RECEIVED MID-THREAD, AND HOW I REWEIGHTED
================================================================================
Both staging and production hold disposable test data; nothing needs preserving.
Reweighted away from data-preservation and rollback mechanics:
  - F10 downgraded Medium -> Low. Kept only because the documentation gap costs a
    paragraph, not because the risk is significant.
  - F1's data-disposition half downgraded. F1 STAYS BLOCKING on F1(b), the
    unvalidated write path, which is a permanent hole in the access model rather
    than a property of today's rows.
  - The migration self-verification recommendation is retained but re-framed: it
    is about not silently legitimising a cross-user reference, not about
    protecting rows.
One finding got STRONGER under the constraint, and it is the one to carry forward:
  - F3's NULL-creator hole is NOT a legacy artefact. cities.createdByUserId is
    ON DELETE SET NULL — deliberately and correctly so — which means every user
    deletion regenerates NULL creators on data created AFTER this ships. Any of
    those still pending become invisible to everyone, permanently. The two choices
    section 4.4 reasons about most carefully combine into a failure its query has
    no branch for.
General principle applied throughout: recoverable is not the same as correct, and
the design ships into a future where the data stops being disposable.
