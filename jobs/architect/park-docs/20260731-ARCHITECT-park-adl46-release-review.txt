THE ONE THING TO KNOW IF YOU READ NOTHING ELSE
F1: POST /api/cities fires resolveCity on the freshly-created pending row (cities.ts:329)
and the 15-minute queue does the same for every pending row; resolveCity's pickBest takes
candidates[0] when the row has no region (geocoding.service.ts:200-211). So the D14
"ask, don't guess" decision — and two GE-16 success criteria — are silently undone within
about a second of a user declining to choose, whenever the geocoder is reachable. The spec
never said what the QUEUE does with ambiguity; the implementation kept the legacy data[0]
behaviour. The fix needs a design decision (my lean: multi-candidate-no-region leaves the
row pending and increments the attempt counter, so the cap bounds it), not a one-liner.
