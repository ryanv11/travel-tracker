========================================================================
INVESTIGATION — WHAT #458 ACTUALLY CHANGED
========================================================================

Read PR #458's merge commit (3dd081095611de79134b53e62cc4f36725434bf0) diff
directly rather than trusting the brief's lead as settled. It:
  - Added src/frontend/hooks/useReviewPanelVisibility.ts (new shared hook).
  - Removed the onClose() call from ReviewPanel's handleLock (the forward
    Lock path) — BUG-58's fix.
  - Rewired both ReviewPanel call sites (TripDetailPage.tsx,
    MobileTripsLayout.tsx) from `onClose={() => navigate('/trips')}` to
    `onClose={dismissReview}` — BUG-86's fix.

The hook's actual mechanism (pre-fix):

  const [dismissed, setDismissed] = useState<{tripId; status} | null>(null);
  const dismissReview = () => setDismissed({ tripId, status });
  const isDismissedForCurrent =
    dismissed !== null && dismissed.tripId === tripId && dismissed.status === status;
  const showReviewPanel = status === 'review_pending' && !isDismissedForCurrent;

THE BUG: `isDismissedForCurrent` compares against ONE stored (tripId,
status) pair. A trip that goes review_pending [dismiss] -> locked [Lock] ->
review_pending [Unlock] ends up back at status 'review_pending' — the SAME
enum value the stale dismissal was recorded against. The comparison matches
again, `isDismissedForCurrent` is still true, and ReviewPanel stays
suppressed. The hook's own doc comment claimed "this trip re-entering
review_pending on a later visit... resets it" — that claim was never true
for a same-value round trip, only for switching to a genuinely different
status or a different trip.

SEPARATE, but same root symptom class: dismissReview was the ONLY way to
flip `dismissed`, and nothing flipped it back except a status change. A
trip that never changes status again after being dismissed has no route
back to ReviewPanel through the UI at all — the brief's second success
criterion ("from the trip view there is a path back to the review page").

The prior hook's own test file's last comment explicitly reasoned this
exact sequence was "not a reachable sequence through the real UI" — proven
wrong by walking the actual button labels: Back to Trip is reachable from
ReviewPanel; once dismissed, TripDetail's stepper for a review_pending trip
shows "Lock Trip" (NEXT_STATUS maps review_pending -> locked); once locked,
the stepper card's Unlock button is reachable. All three are real, existing
buttons — PO clicked exactly this path in UAT.

========================================================================
THE FIX
========================================================================

Two changes to useReviewPanelVisibility.ts, both preserving the "never
navigate to dismiss" invariant #458 established (did not touch ReviewPanel's
onClose wiring, did not reintroduce any navigate() call):

1. dismissed collapsed to a plain boolean. A ref (`seenRef`) tracks the last
   (tripId, status) pair actually rendered. On every render, if the current
   pair differs from seenRef's, the ref updates AND dismissed resets to
   false (if it was true) — a render-phase "adjust state when a prop
   changes" update, the pattern React's own docs recommend for exactly this
   "reset local state when some external value changes" case. It resolves
   synchronously within the same render pass (React restarts the render
   before committing), so there's no one-frame flash of the wrong surface
   the way a useEffect-based reset would produce.

   This means ANY real status transition — not just "away from
   review_pending" but a full round trip BACK to review_pending — now
   clears a stale dismissal. Unlock (locked -> review_pending) is exactly
   such a transition, so it now shows ReviewPanel correctly.

2. New `returnToReview()`: `() => setDismissed(false)`. No status-change
   dependency at all. Exposed alongside `showReviewPanel`/`dismissReview`.

Wired into the trip view:
  - TripDetail.tsx (desktop): new optional `onReturnToReview?: () => void`
    prop. Renders a "Back to Review" button in the stepper card's button
    group (same visual tier as the Unlock button), gated on
    `trip.status === 'review_pending' && onReturnToReview` — the only state
    where "back to review" means anything.
  - MobileTripDetailView.tsx: same prop, rendered as its own callout box
    (matching the existing Unlock callout's treatment) directly below the
    next-step CTA box.
  - TripDetailPage.tsx / MobileTripsLayout.tsx: both destructure
    `returnToReview` from the hook alongside the existing
    `showReviewPanel`/`dismissReview`, and pass it through as
    `onReturnToReview`.

Considered and rejected: reverting to navigation-based dismissal (would
reintroduce the exact blank-panel bug #458 fixed — explicitly the brief's
"don't re-break the direction it fixed" instruction) and an epoch-counter
design (functionally equivalent to the ref-based render-phase reset chosen,
but more state to reason about for no behavioural difference — the simpler
boolean + ref won).

    an integration test that mounts the REAL TripDetailPage component tree
    (TripDetailPage -> useReviewPanelVisibility -> ReviewPanel/TripDetail ->
    useTripDetailController -> real useLockTrip/useUnlockTrip mutations)
    inside a MemoryRouter + QueryClientProvider, with ONLY apiGet/apiPatch
    mocked at the network boundary (mutable in-test "server state" variable

         the trip is never fully deselected, the "blank panel" failure mode
         from the original BUG-86).
      3. A second full dismiss->lock->unlock cycle on the same trip (proves
         "re-locking still works" per the brief's explicit success
         criterion, not just a one-shot fix).
