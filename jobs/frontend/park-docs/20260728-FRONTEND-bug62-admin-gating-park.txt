BUGS DISCOVERED
[FINDING — stale tracker note, corrected, not a code bug]
tracker.json's BRD-AD09 entry (backfilled 2026-03-23) said: "Owner-only
deactivation not enforced — any user can deactivate." GitHub #298's
BRD-AD09 task was written against that premise: "The owner-only
deactivation half is not enforced on the backend today. Enforce it."

Per the mandatory negative-findings rule (CLAUDE.md — any "not
enforced"/"not implemented" claim needs two independent probes before it's
treated as fact), checked this before writing any backend code:

  Probe 1 (code read): src/backend/routes/admin.ts registers
  `adminRouter.use(requireOwner)` at line ~105, BEFORE the categories and
  activities CRUD sub-routers mount at lines ~232-233
  (`adminRouter.use('/categories', createAdminListRouter(...))` etc.).
  Express Router processes middleware in registration order for every
  request that reaches it, independent of when child routers are added
  later in the same file — so every categories/activities route (GET,
  POST, PATCH `/:id` which handles `is_active` updates, and DELETE `/:id`
  which soft-deletes by setting `is_active = 0`) is gated by `requireOwner`
  today.

  Probe 2 (existing test suite): src/backend/routes/__tests__/
  security.access-matrix.test.ts already contains, and already passes:
  "PATCH /api/admin/categories/1 -> 403", "DELETE /api/admin/categories/1
  -> 403", and the same pair for activities — all asserting a non-owner
  authenticated request is rejected.

  Probe 3 (live run, not just trusted the source): ran
  `npx vitest run src/backend/routes/__tests__/security.access-matrix.test.ts
  -t "categories"` in this worktree — 7/7 passed.

  Also grepped repositories/routes for any other write path to
  `isActive` on `tripCategories`/`activities` outside admin.ts — none
  found, ruling out a bypass route.

Conclusion: owner-only deactivation of categories/activities IS enforced on
the backend today. The tracker note was wrong (likely stale since before
`requireOwner` was actually wired into admin.ts, given both the ADL-27
decision and the tracker backfill share a date of 2026-03-23 — plausible
the note was written slightly ahead of the implementation and never
re-verified after). No backend change was made as a result — there was
nothing to fix on this half of AD-09.

BRD-AD09's real, still-open gap is the OTHER half of its text: "Any user
can add custom entries." Category/activity creation (POST) is currently
ALSO behind the same router-level `requireOwner` — more restrictive than
AD-09 specifies, not less. This is the opposite direction from a security
hole (over-restrictive, not under-enforced) and was already correctly
scoped as a separate future brief in ADL-28 Question 5 ("If the COO wants
to open category/activity creation to non-owners per AD-09, that is a
separate brief") — not touched in this thread. tracker.json's BRD-AD09
status stays "partial" for this reason, with corrected notes.

Disposition: flagged here and in the completion report, not fixed
unilaterally — there is nothing to fix on the deactivation side, and
opening creation to non-owners is a product/architecture scope decision,
not something to do unprompted on a brief that asked for the opposite.

CI NOTE — Gitleaks false positive, fixed via allowlist not workflow change
PR #303's first CI run failed one check: Secret Scanning (Gitleaks) flagged
"Categories/Activities/Countries" (three slash-joined capitalized words in
my own BUG-62 tracker.json note) as a generic-api-key match — an
entropy/shape heuristic misfire, confirmed not a secret by reading the
source line directly. Reworded the note for clarity, but gitleaks scans the
full commit history by default (`fetch-depth: 0`), so the flagged text
stayed present at the earlier commit regardless of a later rewording commit
— rewriting that commit's history (amend/force-push) was avoided per the
git safety protocol, so instead added `.gitleaks.toml` at the repo root: an
allowlist entry matching gitleaks' own reported match string exactly
(narrow — suppresses only this literal 50-character phrase, not the whole
file or commit), which `./gitleaks detect --source=.`
(.github/workflows/security.yml, unchanged) picks up automatically with no
workflow edit. Verified locally with the same pinned gitleaks v8.30.1
binary + sha256 the workflow uses: 1 leak → 0 with the config in place, full
355-commit history scanned. PR #303 is now 9/9 green.
