WHAT CHANGED

1. BUG-71 (P1) stopgap — src/frontend/components/TripDetail/AddPlaceFlow.tsx

   Observed: typing "springfield" into Add Place on staging pre-populated the
   State field with "Virginia," no ambiguity hint of any kind.

   Mechanism, confirmed by reading the code: the new-city form's geocode
   lookup collects `sameCountryRegionIsos` (distinct non-null region_iso
   values among candidates sharing the resolved country). When that set has
   more than one entry, D14's existing multi-candidate narrowing kicks in
   (unchanged, out of scope here). When it has exactly one (or zero, falling
   through to the top candidate's own region), the code silently commits that
   single value via `setAutoRegionIso` -> an effect that sets
   `newCityRegionId` directly. The upstream cause (also out of scope, per the
   brief): GET /api/geocode queries Nominatim globally at limit:10, so a
   globally-ambiguous name (many Springfields worldwide) can have its 10
   slots thinned by settlement-type filtering and the frontend's
   non-null-region_iso requirement down to exactly one same-country survivor
   — indistinguishable, at the frontend, from a name that is genuinely
   unambiguous (Denver: multiple Nominatim hits, but all the same one real
   region).

   Explicitly out of scope per the brief (endorsed by two prior OP-27
   reviews): truncation detection, changing the geocode request shape, a
   candidate shortlist selector, any backend change. The fix does not and
   cannot tell the false-single-survivor case apart from the genuine one —
   it doesn't try to. Instead, EVERY auto-fill from the single-candidate path
   is now treated identically: pre-filled (not blanked — blanking would trade
   a wrong answer for no answer, a UX regression on the ordinary Paris/Denver
   case) but rendered as visibly tentative.

   Concretely: new `regionIsSuggested` boolean state, set true only inside
   the `else if (regionIso)` auto-fill branch (mutually exclusive with the
   D14 ambiguous branch, which sets `candidateRegionIsos` instead and never
   this flag). When true and the D14 ambiguous hint is NOT also showing,
   renders a caption under the region <select>:
     Suggested: {region name} — from "{city name}"
   reusing the UX spec §3.2 "Suggested:" chip pattern verbatim (written there
   for the country field's tier-3 fallback guess) rather than inventing new
   wording — the brief was explicit this pattern should be adopted, not
   redesigned. Cleared (regionIsSuggested -> false) the instant: the user
   picks a region themselves via the select's onChange (tier 1 of the UX
   spec's precedence rule: an explicit choice is never "just a suggestion"
   again); the user changes the country (invalidates the whole auto-detected
   state, same as the pre-existing autoRegionIso/candidateRegionIsos resets
   there); or the new-city form is reopened for a fresh lookup.

   NOT changed: the D14 multi-candidate narrowing branch, the geocode
   request/response shape, BUG-73's failure banner/Retry path (verified
   still green — see VERIFICATION).

2. BUG-72 (P2) — src/frontend/components/TripDetail/AddPlaceFlow.tsx,
   src/frontend/types/api.ts

   Observed: the search dropdown rendered one line per row as
   `{city.name} {city.country_code}` — "Springfield US". Selecting a row
   binds the trip to one specific `cities` row with specific coordinates,
   with nothing on screen identifying which Springfield.

   Verified the brief's claim myself before building on it (brief explicitly
   said not to take its word for it): read src/backend/routes/cities.ts's
   GET /api/cities handler directly — it already LEFT JOINs `regions` and
   selects `region_name`/`region_iso` per row (BUG-72's backend half, PR
   #353, landed 2026-08-01 per `git log`). Cross-checked the frontend
   `City` type (src/frontend/types/api.ts) — it had `region_iso` already but
   NOT `region_name`. Two consistent signals (backend route reads the
   column; frontend type doesn't have it), no contradiction to resolve.

   Added `region_name?: string | null` to the `City` interface — optional,
   not just nullable, because it is genuinely absent (not merely null) from
   every OTHER City-shaped response in the app: `serializeCity` (cities.ts,
   used by POST/PATCH) and the trip-detail/map City shapes never select the
   column at all. Making it required would have meant touching City fixture
   literals in CityMarkers.test.ts, ReviewPanel.test.tsx, PlaceSection.test.tsx,
   TripDetail.test.tsx, and filterAndSortTrips.test.ts across the app for no
   functional reason (confirmed via `npm run type:check:all`, which failed
   with exactly those five call sites when I first tried region_name as
   required) — optional matches what's actually true of the API surface and
   avoids scope creep into five unrelated test files for a two-component bug
   fix.

   New `formatCitySubtitle()` helper (AddPlaceFlow.tsx): for a region-tier
   country's row with a region, renders "{region name}, {country code}"
   (e.g. "Illinois, US"); for a region-tier country's row with NO region,
   renders "{country code} (no {region label} set)" (e.g. "US (no state
   set)") — explicitly distinct wording, never visually identical to a
   regioned row, per the brief's requirement that missing-region catalogue
   pollution stay visible to users (a deliberate prerequisite the UX spec
   names for later correction work). Non-region-tier countries render
   unchanged (just the country code) — no behaviour change for the common
   case. No new network call: reuses the `countries` list AddPlaceFlow
   already had loaded via the existing `useCountries()` call.

   Added a `data-testid={`city-search-result-${city.id}`}` to each search
   result row — no prior test exercised this render path at all (the
   existing D14 test file mocks `useCitySearch` to always return `[]`), so
   there was no existing query strategy to reuse.
