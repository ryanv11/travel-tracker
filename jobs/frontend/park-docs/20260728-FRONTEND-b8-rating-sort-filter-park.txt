DESIGN DECISION — client-side (PlaceSection) vs. server-side (CityItemsPage)
  PlaceSection's place.items arrives pre-loaded, nested inside the trip
  detail fetch (GET /api/trips/:id via TripDetail's own data flow). Grepped
  src/backend/routes/trips.ts's buildTripResponse for sort_by/min_rating —
  no match; that nested endpoint has no sort/filter query support at all
  (only the flat /api/trips/:tripId/items and /api/cities/:id/items
  endpoints do, per items.ts:38 and cities.ts:329). Two options: (a)
  restructure PlaceSection to fetch its own items per-place via the flat
  endpoint with query params, or (b) sort/filter client-side over the data
  already in hand. Chose (b): applyRatingSortFilter() in useItems.ts is a
  pure function over Item[], used as local component state in PlaceSection
  (useState<RatingSortFilterState>, reset to DEFAULT_RATING_SORT_FILTER).
  Reasoning: (a) would touch TripDetail's data-fetching architecture, which
  concurrent brief B7 is actively working in the same window — real
  collision risk for no user-visible benefit, since items are already
  loaded and (b) needs no extra network round-trip per sort/filter toggle.
  (b) also gives IT-08's "state does not leak between trips" for free:
  place.id differs across trips, so switching trips fully remounts each
  PlaceSection with fresh local state — no explicit reset logic needed.
  CityItemsPage, by contrast, calls GET /api/cities/:id/items directly (a
  dedicated flat endpoint, no nested-response constraint) — sort/filter
  there is real server-side query params via useCityItems, which already
  matches the endpoint's own default behaviour (rating DESC, unfiltered,
  when no params given).
  Both surfaces share one RatingSortFilterControls component (new,
  src/frontend/components/shared/) so the control shape/labels are
  identical regardless of which side does the actual sorting — satisfies
  IT-09's "behaves identically to the trip-level view."

UNRATED-ITEM SEMANTICS (matched to backend, verified by reading it)
  Read src/backend/routes/items-helper.ts and cities.ts in full: both
  filter with `effectiveRating != null && effectiveRating >= minRating`
  (never coerces null to 0), and default sort on ties/no-sort-param falls
  back predictably. applyRatingSortFilter() mirrors this: minRating filter
  excludes any item with rating === null outright; sortOrder places
  rating === null items last regardless of asc/desc direction (matching
  the flat items endpoint's own "nulls last" test,
  src/backend/routes/__tests__/items.rating-sort-filter.test.ts).
