PLAYWRIGHT GOTCHAS HIT AND FIXED (worth remembering for future spec authors)
  1. Strict-mode violations ABORT IMMEDIATELY — they do not retry through
     ambiguity the way a simple "not yet visible" does. A substring
     `getByText()` failed a `not.toBeVisible()` assertion in <100ms (not at
     the 5s timeout) because a ConfirmDialog's title/message repeated the
     target city name as a superset string. Fix: `{ exact: true }` or a
     testid-scoped locator whenever a superset-text sibling could exist even
     transiently.
  2. `getByLabel` only associates `<label>`-linked FORM controls — RatingStars
     renders a plain `<span aria-label="...">`, which needs a CSS attribute
     selector (`locator('[aria-label="..."]')`), not `getByLabel`.
  3. ADL-14 "lazy creation on first rating": `POST .../items` silently drops a
     `rating` field at create time (by design) — must PATCH it in afterward.
     Cost me one failed test before finding the repository comment explaining
     this.
  4. Carry-forward's wire format is snake_case (`source_item_ids`) — the
     frontend hook (`useCarryForward`) takes camelCase params but translates
     them; a raw API call for E2E seeding must use the wire name directly.
  5. Two pre-existing specs needed intentional updates, not drift-chasing:
     - trips-crud.spec.ts: `getByText('New Trip')` → `getByRole('heading', {
       name: 'New Trip' })`, since the desktop button is now labelled
       "+ New Trip" (was "+ New") per spec, and the old substring locator
       became ambiguous against the new button text.
     - trips-filters.spec.ts: placeholder locator text updated to "Search
       trips or places…" per spec's explicit copy fix (search already matched
       place names; the shorter placeholder undersold existing behavior).

BUGS DISCOVERED

  [MAJOR] items.carriedFromItemId has no onDelete FK behavior — disposition: FLAGGED TO COO, NOT FIXED (out of Frontend's remit)
    INITIAL CLASSIFICATION: MAJOR (discovered directly at this severity, not
      via reclassification).
    ACTUAL CLASSIFICATION:  MAJOR.
    DISCOVERY CONTEXT: Writing the new "carried-forward tag survives the
      reskin" E2E test — creating a source trip with a next_time item,
      executing the real POST .../carry-forward endpoint against a second
      (target) trip, then letting the next spec file's blanket
      `deleteAllTrips()` cleanup run.
    SYMPTOM: DELETE /api/trips/:id on the SOURCE trip returns 500 Internal
      Server Error if any item created via carry-forward (in ANY other trip)
      still has `carried_from_item_id` pointing at one of the source trip's
      items.
    ROOT CAUSE: `src/backend/db/schema.ts`'s `items.carriedFromItemId` column
      declares a self-referencing FK (`.references(() => items.id)`) with no
      `.onDelete(...)` clause — SQLite's default FK behavior (effectively
      RESTRICT under enforced foreign_keys) blocks deleting a still-referenced
      row.
    SCOPE: Any trip deletion where one of its items was ever used as a
      carry-forward source for an item in ANY other trip (including trips
      that have themselves since been otherwise modified/locked/unlocked —
      the reference persists independent of trip status). Likely also blocks
      deleting the individual SOURCE ITEM directly (not just whole-trip
      deletion) if that's ever exposed as an operation without deleting the
      whole trip.
    PROPOSED FIX: `carriedFromItemId: integer('carried_from_item_id')
      .references((): AnySQLiteColumn => items.id, { onDelete: 'set null' })`
      — semantically correct: deleting the source item shouldn't cascade-
      delete the derived item, just clear its provenance link. Requires a
      migration (db:generate + db:migrate) and Architect + Database review
      per CLAUDE.md's schema-change rule — NOT something Frontend can or
      should apply unilaterally.
    BLOCKING: Not blocking this PR — pre-existing defect (not introduced by
      this reskin), and my new E2E test cleans up after itself in the correct
      order (delete the referencing/target trip before the referenced/source
      trip) so it doesn't leave the suite in a broken state. Real users hitting
      this in production (delete a trip after one of its items was carried
      forward elsewhere) would see an unrecoverable 500 on trip deletion,
      though — recommend a tracker entry + Database/Architect brief soon,
      not indefinitely deferred.

  [TRIVIAL] Environment gap — fresh worktree missing .env.local — disposition: worked around, flagged
    Not a code bug. A fresh git worktree does not inherit `.env.local`
    (unshared/unsymlinked, same category as the already-documented
    node_modules gap in CLAUDE.md). `npm run test:e2e`'s webServer failed with
    `DB_TYPE: "undefined"` fatal startup error until I created one (copied
    from `.env.example`, `DB_TYPE=sqlite`; correctly gitignored, never staged/
    committed). Re-evaluated per rule 26: does this touch shared state/a query
    used elsewhere? No — purely a local dev-environment bootstrap gap, same
    root cause and same fix pattern as the node_modules note. Kept at TRIVIAL.
    Recommend COO add this to CLAUDE.md's worktree-isolation guardrails
    alongside the node_modules note (not actioned in this brief — that's a
    CLAUDE.md edit, outside Frontend's remit and outside this brief's scope).
