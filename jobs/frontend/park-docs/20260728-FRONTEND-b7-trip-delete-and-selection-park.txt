BUG-50 / TR-14 — DELETE AFFORDANCE
  Anchors from the brief, confirmed before building (not re-probed, brief
  states these were already double-probed): tripsRouter.delete('/:id')
  exists at src/backend/routes/trips.ts:429, userId-scoped, 403s on locked
  trips, cascades; useDeleteTrip already exists (useTrips.ts:168) and is
  wired to bulk delete in both list layouts; ConfirmDialog exists in
  components/shared/. Frontend-only — no backend route added.

  Design decisions made during implementation, in order of how load-bearing
  they are:

  1. Delete logic lives in useTripDetailController.ts (shared by
     TripDetail.tsx and MobileTripDetailView.tsx already, for status/lock/
     unlock), not duplicated in each component. Added state (confirmDelete),
     the useDeleteTrip() mutation, and three handlers: handleDeleteClick
     (opens the dialog, resets any stale mutation error — same precedent as
     PlaceSection's handleOpenRemoveConfirm), handleDeleteConfirm (the real
     delete: mutateAsync then navigate('/trips', { replace: true }) —
     mirrors the exact call shape already used by both layouts' bulk-delete
     "if the currently viewed trip was deleted, navigate away" branch), and
     handleDeleteDialogConfirm (the dialog's actual onConfirm — branches on
     isLocked before deciding whether to call handleDeleteConfirm at all).

  2. Locked-trip handling: TR-14 says "not deletable without unlocking
     first" AND "attempting to delete a Locked trip is refused with a
     message directing the user to unlock" — both must be true at once,
     which rules out simply hiding the button (Edit's pattern) since a
     hidden button can't be "attempted." Decision: the Delete button stays
     visible/reachable even when locked (documented as a deliberate
     exception in TripDetail.tsx's module doc, next to the general "hide
     write controls when locked" rule). Clicking it always opens
     ConfirmDialog; when isLocked, the dialog's copy switches to "This trip
     is locked... Unlock this trip first" with confirmLabel "Unlock Trip",
     and clicking that button doesn't call the delete mutation at all — it
     closes confirmDelete and opens confirmUnlock, i.e. routes straight into
     the pre-existing unlock flow. This was a deliberate choice over letting
     the click hit the real API and surface the backend's LockError message
     ("Trip is locked", not directive) — client-side short-circuit avoids
     duplicating the lock/unlock RULE (which decision requires no backend
     round-trip since trip.status is already known) while still being more
     actionable than a bare error string. Flagging this as a design call
     worth a second look: it does mean a genuinely stale client (trip
     status changed server-side between page load and click) would show
     "locked" copy even after a real unlock elsewhere, until the next
     query refetch — a narrow edge case, not exercised by tests, not
     believed to be a regression risk given the existing 5-minute staleTime
     and this UI's general refetch-on-focus behavior, but noted rather than
     silently assumed fine.

  3. Confirmation copy: computed in each component (TripDetail.tsx /
     MobileTripDetailView.tsx), not the shared hook — deliberately, since
     hooks/logic vs. presentation-text felt like the right split, and the
     two components' copy is currently identical (kept simple rather than
     centralizing text into the hook prematurely). Names trip name, place
     count, item count; branches to a shorter message when placeCount is 0.
     Pattern lifted directly from PlaceSection's remove-place dialog
     (place.items.length > 0 branch).

  4. New TrashIcon.tsx (not pre-existing) — the bulk-delete action bar uses
     a bare text label, no icon existed for this. Added to the icons
     barrel, icons.test.tsx's ALL_ICONS array and count assertion updated
     (13 -> 14) since that test enumerates every icon by name.

  5. Accessible naming: the desktop button and the dialog's confirm button
     for the SAME action ("Delete Trip") share their accessible name once
     the dialog opens — same collision shape as ReviewPanel's pre-existing
     "Return to Planning" trigger-vs-confirm-button pattern. Gave both
     desktop and mobile trigger buttons aria-label="Delete Trip" (desktop's
     visible "Delete" text is aria-hidden, matching how the icon is already
     aria-hidden) for a consistent, unambiguous accessible name across
     breakpoints — tests disambiguate the two same-named buttons via
     getAllByRole()[1], same technique already used for Lock/Return-to-
     Planning in ReviewPanel.test.tsx.

  KNOWN GAP, surfaced not fixed: a review_pending trip renders
  ReviewPanel.tsx (via TripDetailPage's status branch / MobileTripsLayout's
  renderDetailContent), not TripDetail.tsx/MobileTripDetailView.tsx — so it
  currently has NO delete affordance at all. The brief's own anchors ("grep
  across TripDetail.tsx and MobileTripDetailView.tsx returns nothing")
  scoped the probe to exactly those two files, and TR-14's "reachable from
  the trip detail view" doesn't explicitly settle whether ReviewPanel counts
  as part of "the trip detail view" for this purpose. Did not expand into
  ReviewPanel.tsx unilaterally — flagged to COO in the completion report and
  tracker note instead.

BUG-58 — ROOT CAUSE AND FIX
  The only user-reachable backward transition in the status workflow is
  "Return to Planning" (review_pending -> planning, BUG-04's fix) inside
  ReviewPanel.tsx. Its handler, handleReturnToPlanning, called onClose()
  unconditionally right after the status mutation resolved. onClose is
  wired one level up: TripDetailPage passes `() => navigate('/trips')` and
  MobileTripsLayout passes `handleBack` (`() => navigate('/trips')`) — both
  drop the trip's :id from the route, clearing selection in the exact same
  click that changes status. This is a precise match for the bug report:
  "Moving a trip backward... clears the selection entirely."

  The OTHER backward transition — Unlock (locked -> review_pending, in
  useTripDetailController) — never called onClose() to begin with and was
  already correct per the brief's own "Expected: the trip stays selected"
  description. Confirmed this with a new test
  (useTripDetailController.test.tsx: "handleUnlockConfirm ... does not
  navigate") rather than relying on inspection alone, since the brief
  explicitly says "Verify the actual mechanism before fixing it; that
  hypothesis is mine, not established" about its OWN filter-drop hypothesis
  — worth the same discipline toward my own read of the code.

  Fix: removed the onClose() call from handleReturnToPlanning. The status
  mutation invalidates ['trips'] and ['trips', tripId] (useUpdateTripStatus,
  unchanged), which is sufficient — once trip.status flips to 'planning',
  TripDetailPage/MobileTripsLayout's own status branch stops rendering
  ReviewPanel for this :id and renders TripDetail/MobileTripDetailView
  instead, no navigation needed, same trip still selected.

  Deliberately NOT touched: ReviewPanel's handleLock (forward,
  review_pending -> locked) has the exact same onClose()-after-mutation
  shape. This is very likely the same underlying design mistake, but it's a
  FORWARD transition, was not the bug as filed ("moves backward"), and
  fixing it wasn't asked for. Flagged to COO in the completion report and
  tracker note as a related-but-separate possible follow-up rather than
  silently expanding this brief's scope.

  Also confirmed (brief's own instruction): "make sure your BUG-58 fix
  doesn't break [BUG-50's] deleting the selected trip obviously should
  clear selection" — handleDeleteConfirm's navigate('/trips', {replace:
  true}) call is untouched by the BUG-58 fix (different file, different
  handler), and TripDetail.test.tsx/MobileTripDetailView.test.tsx both
  assert the post-delete navigate still fires.

ADDENDUM — CI E2E failure found and fixed after initial push
  First push (commit f3a7bf8) went green on every check except E2E Tests:
  src/e2e/places-items.spec.ts's "delete item with confirmation" failed —
  its own item-level Delete button lookup, `getByRole('button', { name:
  'Delete' }).first()`, started matching the NEW trip-level "Delete Trip"
  button too (Playwright's default `name` match is substring, not exact,
  and "Delete Trip" contains "Delete"; the trip-level button also renders
  earlier in the DOM, above Places/Items, so `.first()` picked the wrong
  element and the item's own confirm dialog never opened). Fixed by adding
  `exact: true` to that one lookup (commit ddfe3ad) — the item's own button
  has no aria-label, so its accessible name is exactly "Delete", which
  `exact: true` isolates cleanly from "Delete Trip". Verified the fix
  properly rather than just re-pushing and hoping: reproduced locally
  (created a throwaway .env.local with DB_TYPE=sqlite, since this worktree
  doesn't have one and Playwright's webServer needs it; deleted it again
  before finishing, it's gitignored so it was never at risk of being
  committed), ran the full Playwright suite (52/52 green) plus the specific
  previously-failing test individually, then re-pushed. Also grepped every
  e2e spec file for other `name: 'Delete'`-shaped matches before declaring
  this fixed (not just the one that failed) — two others exist
  (trips-crud.spec.ts, trips-mobile.spec.ts's bulk-delete tests) but both
  run against /trips with no trip selected, where TripDetail/
  MobileTripDetailView never mounts, so the new button was never in scope
  for those and they were unaffected (confirmed green both before and after
  this fix). scripts/ci-wait.sh pr 319 reported PASS — all 18 checks green
  — on the second push.
