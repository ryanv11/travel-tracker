SUMMARY

useAdmin.ts's five companion hooks were still pointed at /api/admin/companions,

BUGS DISCOVERED
[MAJOR] Non-owner authenticated users cannot reach the Companions tab at all —
  disposition: escalated to COO (FLAG-AD08-1 in context/current.txt), not
  fixed in this thread.
  Initial expectation (per brief): CompanionTab.tsx might contain an isOwner
  check gating the tab's own visibility/content. It does not.
  Actual finding: the gate is one layer up — App.tsx wraps the entire /admin
  route in <RequireOwner> (renders "Not authorised" for non-owners, nothing
  while loading) and the "Admin" NavLink itself only renders when
  `!!me?.isOwner`. Both are BUG-26's deliberate, tested contract
  (src/frontend/__tests__/App.test.tsx, 6 tests spanning nav-link visibility
  and the /admin route guard, all currently passing and asserting exactly
  this owner-only behaviour).
  Why not fixed here: AD-08's design (ADL-28) says companions move to "any
  authenticated user", which the backend now enforces correctly. But making
  that true end-to-end on the frontend requires replacing the page-level
  RequireOwner gate with per-tab gating inside AdminPanel.tsx — since the
  other four tabs (categories, activities, shading, countries) correctly
  remain owner-only per SE-03's narrowed scope (ADL-28 Q4). That's a real
  architecture change to shared nav/route code, not a two-line hook fix, and
  it directly reverses part of a different, separately-tracked bug's (BUG-26)
  tested behaviour. The brief's own contingency language ("If it does, that's
  an AD-08 access-control fix in scope for this brief") anticipated a
  component-local gate, not a page-level one shared with four still-owner-
  only tabs — so I judged this materially different from what was
  pre-approved and stopped short of implementing it, flagging instead.
  Precedent for routing this to COO/Architect rather than patching directly:
  tracker.json's BRD-AD07 entry documents exactly this pattern for a
  different auth-scoping gap (GitHub #225, resolved via ADL-38) — "Routed to
  Architect first per this project's established pattern for auth-scoping
  changes... rather than a unilateral Backend patch."
  Scope of impact: presentation-layer only (backend already correctly scopes
  companions to req.user.id regardless of who can reach the tab) — no data
  leakage, no security regression. It's a usability/completeness gap: AD-08
  is not yet actually usable by non-owner users, even though its backend and
  hook layers are both now correct.
  Blocking: does not block this PR. Companions were equally unreachable for
  non-owners before this fix (the route 404'd), so this fix is a net
  improvement (owners can now use companions correctly) even though it
  doesn't close the non-owner reachability gap.
  Proposed fix (for the follow-up brief): move RequireOwner off the /admin
  route entirely; gate individual tabs inside AdminPanel.tsx (companions
  visible/usable by any authenticated user; categories/activities/shading/
  countries stay owner-only, hidden + content-gated exactly as RequireOwner
  did at the page level); change the Admin NavLink to render for any
  authenticated user (matching Map/Trips); update App.test.tsx's BUG-26
  assertions to match the new per-tab contract.
