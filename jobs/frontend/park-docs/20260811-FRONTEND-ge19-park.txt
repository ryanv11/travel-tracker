KEY DESIGN DECISIONS / THINGS A REVIEWER SHOULD KNOW
================================================================================
1. NEEDS-ATTENTION VISUAL TREATMENT — FLAGGED FOR PO UAT (COO instruction).
   No UX mockup specified this. Chosen default: the needs-attention badge is an
   amber warning chip ("⚠ N need attention", border-amber-500/bg-amber-50);
   the resolving chip is muted/neutral ("☁ M resolving"). In the panel,
   needs-attention rows have an amber card + ⚠ label; resolving rows are muted
   with a ⟳. This is a sensible default, NOT final — PO should confirm or
   redirect during UAT.

2. CITY→PLACE JOIN FOR RECOVERY (the one contract-shape decision).
   GET /api/geocode-queue returns CITIES, but re-point and remove are place
   operations ({tripId, placeId}). Rather than ask backend for a place id on
   the queue shape, the join derives from useTrips (GET /api/trips), which the
   app already loads and whose places carry city_id. This is NOT a second
   source of truth: the queue owns "which of my cities are stuck", the trips
   list owns "which of my places reference that city". Every queue city has ≥1
   referencing place by construction — the queue and the trips list both derive
   from the same userId-scoped trip_places → trips join. This is the honest fix;
   it did not require a backend/contract change.

3. LOCALSTORAGE RETIREMENT — two-probe negative check (CLAUDE.md rule).
   Probe A: grep across src for geocodeRetryQueue / useGeocodeRetryQueue /
   GEOCODE_RETRY_STORAGE_KEY / 'geocode_retry_queue' — non-test readers were
   only App.tsx (badge) and AddPlaceFlow.tsx (.add()). Probe B: grep every
   localStorage usage in src/frontend for geocode/retry — the key is
   read/written ONLY inside geocodeRetryQueue.ts. Nothing else load-bearing
   reads it, so the four files were safely deleted. Server-side processQueue is
   untouched — only the badge's read-source changed.

4. NO "dismiss" / retry buttons. OQ-1: no soft-dismiss (removing the place is
   the only clear). Retry is server-driven (processQueue), so the old client
   retryAll/dismiss are gone with the localStorage service.

5. "extend the pending-indicator component" — there was NO standalone indicator
   component; the badge was inline JSX in App.tsx. I extracted it into a real
   component and extended its behaviour (not a parallel second badge). Flagged
   to COO as a minor brief-vs-reality mismatch, not a deviation.
