BUGS DISCOVERED / CORRECTED
  [FINDING, not a bug — a stale tracker note] BRD-AD09's tracker note
  (backfilled 2026-03-23) claimed "Owner-only deactivation not enforced —
  any user can deactivate." This is what #298 bundled a backend task on.
  Checked with three independent probes before writing any code:
    1. Code read of src/backend/routes/admin.ts:
       `adminRouter.use(requireOwner)` (line ~105) is registered BEFORE the
       categories/activities CRUD sub-routers mount
       (`adminRouter.use('/categories', ...)` / `.../'activities'`, lines
       ~232-233). Express processes router middleware in registration
       order regardless of when sub-routers are added later, so every
       categories/activities route — GET, POST, PATCH, DELETE, including
       the PATCH/DELETE deactivation paths — is owner-gated today.
    2. src/backend/routes/__tests__/security.access-matrix.test.ts already
       has explicit tests: "PATCH /api/admin/categories/1 -> 403",
       "DELETE /api/admin/categories/1 -> 403", same pair for activities,
       for a non-owner authenticated user.
    3. Ran that test file live in this worktree (not just trusted the
       source): `npx vitest run ... -t "categories"` -> 7/7 passed.
    Also grepped repositories/routes for any other write path to
    categories/activities `isActive` outside admin.ts — none found.
  Conclusion: deactivation IS owner-only enforced on the backend today.
  BRD-AD09's real, still-open gap is the OTHER half of its text ("Any user
  can add custom entries") — creation (POST) is also behind the same
  router-level requireOwner, which is MORE restrictive than AD-09
  specifies, not less. That's the opposite direction from a security gap
  and is explicitly out of scope for this brief (ADL-28 Question 5 already
  calls it out as "a separate brief" if the COO wants to open it).
  tracker.json's BRD-AD09 note corrected accordingly; status left "partial"
  since a real gap remains, just not the one previously described.
  Disposition: flagged to COO in this park doc and the completion report,
  not fixed unilaterally (nothing to fix on the deactivation side; the
  creation-scope question is a product/architecture call, not mine to make
  unprompted).
