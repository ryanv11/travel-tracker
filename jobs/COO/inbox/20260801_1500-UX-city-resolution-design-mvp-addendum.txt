WHAT WAS ADDED
Two new sections appended to the same spec (jobs/ux/tech/20260801-UX-city-entry-and-
disambiguation-spec.md), per two follow-up COO messages the same day:

§11 — a single recommended resolution design (not a menu) for how a user fixes an
unlocated place, shown as four worked flows with named examples (Springfield/no state
chosen, offline-created Lyon, an unresolvable fictional hamlet, wrong-Rome-Georgia), per
explicit PO instruction. Confirms the "cause must be visible" structural question with one
refinement: visible only down to where the remedy changes (three buckets, not the backend's
four internal dispositions). Adds a promotion rule the backend ruling doesn't itself
provide — a `pending` row past its retry cap must read as terminal in the UI even though
the backend never marks it `unresolvable`. Reasoned, independent agreement with rejecting
the user-authored-pin idea (not deference) — one place named where the COO's own argument
is weaker than stated.

§12 — an MVP scope, after a second message reframed this as probably-edge-case-until-
measured. Verified both COO-relayed claims myself: the release branch's
UpdatePlaceDatesSchema does accept an optional city_id (confirmed independently in the
schema file and the route), but I concluded PlaceDateForm.tsx is the WRONG surface to
extend (genuinely dates-only, extending it is scope creep) — recommend a separate, equally
small modal instead. MVP: standing Change City control (unconditional) + one
undifferentiated badge, zero new hues + the cheap country-safeguard and creation-time
messaging kept in. Everything else (bucket split, one-tap picker, map counter, Dismiss)
deferred with concrete triggers. Two items named explicitly NOT safe to cut: the standing
control itself, and some passive signal a location isn't confirmed.
