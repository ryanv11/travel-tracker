SECURITY CHECKLIST (route modified: GET /health)
1. AUTH — /health is intentionally unauthenticated (OP-06 §1.2 liveness-probe exemption), sits
   outside /api/ and so outside the blanket requireAuth mount. Unchanged by this brief. The
   payload exposes ONLY commit / commitFull / builtAt: no env values, no config, no filesystem
   paths, no dependency versions. The resolver's `source` field is logged at startup and never
   serialised over HTTP. Both new test files assert the EXACT key set, so a future addition fails
   a test rather than shipping. The public-repo argument covers the SHA and is not extended
   further.
2. USERID SCOPING — N/A, and confirmed: the handler touches no repository, no database and no
   request context at all. It reads two env vars and one build-time JSON file. No user data is
   reachable through this change.
3. FK .notNull() — N/A. No schema change, no migration, no edit to schema.ts anywhere in this
   branch.

RAILWAY_GIT_COMMIT_SHA — three probes, and one thing left UNVERIFIED
(a) COO's list-variables: not listed. Blind spot confirmed real — get-service-config's
    variableNames shows the same 11 user-set app variables and NO platform-injected ones at all
    (not even RAILWAY_PROJECT_ID), so that API's silence is expected behaviour, not absence.
(b) Railway docs: system variables go to "all builds and deployments"; Git variables apply when
    the deploy originates from a GitHub trigger.
(c) Empirical and independent: service source is ryanv11/travel-tracker@main, and every staging
    deployment's meta carries commitHash + branch:main — (b)'s precondition holds in fact.
Runtime injection is EXPECTED, but no probe observed the deployed process's environment and the
staging origin is firewall-blocked here, so runtime presence is UNVERIFIED. The build-time baked
file exists precisely so the feature does not depend on that claim being true.
