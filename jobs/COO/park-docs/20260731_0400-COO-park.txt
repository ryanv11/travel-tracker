## 1. The ADL-46 release is now in flight — delivery model matters, read this
ADL-46 ships as ONE release (PO decision, §9.1) across three stages: Database → Backend → Frontend.
The DB stage (#333) is *red by design* — making categories/activities `user_id NOT NULL` breaks every
backend insert site until the Backend stage catches up (4 CI jobs fail: Type Check, Backend Tests,
Contract, E2E). Merging that to main would break staging.

**Resolution (ADL-47): integration branch.** `release/adl46-access-model` off main; each stage merges
into it (red is fine on the integration branch — it is NOT main); one final PR → main when the whole
release is green. main never red. Backend and Frontend agents branch off the integration branch, not
main. DO NOT merge any single stage to main on its own.

TWO things the agent surfaced, both real:
  a) **ADL-46 §9.3.3's assertion SQL was invalid.** `SELECT RAISE(ABORT,...) WHERE EXISTS(...)` only
     works inside a trigger body in SQLite/libSQL — it would never have run. The review appendix
     *described* it in a comment and never executed it, so it passed OP-27 review. Agent replaced it
     with a scratch-table-named-CHECK construct that genuinely aborts+rolls back, verified firing.
     Sound fix. → PROCESS NOTE for OP-27: a review that "executes" a migration can still miss a block
     it only described. "Executed" ≠ "executed every block". Candidate D-entry next session.
  b) The real release risk is NOT the DDL (validated) — it is **D13's three-step find-or-create
     wildcard-upgrade** (Backend stage). Get it wrong → silently recreates BUG-33 duplicate cities.
     Weight the Backend brief's review there.
